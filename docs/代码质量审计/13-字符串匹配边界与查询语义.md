# 13 字符串匹配边界与查询语义

- **状态**：已完成（三刀 v0.0.1656 落地）
- **日期**：2026-11-27
- **基线**：`e9d27978`（12 全案三刀落地后，`origin/main` 最新）
- **审计范围**：`internal/` 生产代码中「用户输入进入 SQL LIKE 模式」的查询语义正确性——`%`/`_` 通配符是否被转义、转义值是否配 `ESCAPE` 子句。核心是 3 处已转义（团队已认知）vs 9+ 处搜索端点完全未转义（治理缺口）；并核验 `ptgen_handler.go` 转义值缺 `ESCAPE` 子句的深层同型、黑名单空串恒命中、外部尺寸溢出等次要候选。
- **审计方法**：全库扫描 `LIKE ?` 的参数拼接点，逐条读上下文区分「已转义/未转义/转义但缺 ESCAPE」；用 Python 内存 SQLite（`:memory:`）离线复现通配符劫持与 `ESCAPE` 缺失两种语义；对照 04（入参契约）/05（DB 访问纪律）划清正交边界；对盘点中排除的维度（正则捕获组/时间/GORM 语义/整数除法/循环 defer/uint 下溢/slice 别名）独立复核确认健康。
- **证据文件**：`evidence/tool-versions.txt`（工具版本+基线）、`evidence/like-wildcard-repro.txt`（内存 SQLite 真实输出）。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。所有证据均来自本地内存 SQLite 伪数据，未接触靶机或真实用户数据。

## 1. 结论摘要

- 本篇是全库盘点后新立的独立方向，治理对象是**查询结果的语义正确性**——用户输入的字符串作为 LIKE 模式时，`%`/`_` 是否被当作通配符劫持查询。与前序篇正交：04 管 HTTP 入参校验/分页/错误码契约（"输入怎么被接受"），05 管 `WithContext`/无界查询/索引性能（"查询怎么被发起"），本篇管"查询结果对不对"（通配符语义）；09/12 管 HTTP 资源与限流状态机，不重叠。
- **确认一组真缺陷（V-01，中危）**：项目内**已有 3 处正确转义**（团队已认知该问题），但 9+ 个搜索端点把 `r.URL.Query().Get("search")` 等用户输入直接拼成 `"%"+search+"%"`——参数绑定防住了 SQL 注入，但 `%`/`_` 作为 LIKE 通配符未被转义，用户输入 `%` 时模式变成 `%%%` 命中全表、`_` 时 `%_%` 同样全命中，搜索框完全失去过滤作用。离线实测确认。
- **深层同型（V-02，中危）**：`ptgen_handler.go:84` 被当作"正例"——它把 keyword 转义为 `\%`/`\_`，但两条 `LIKE ?` **都没带 `ESCAPE '\'` 子句**。SQLite/MySQL 下无 `ESCAPE` 时反斜杠是字面量，`\%` 匹配的是字面 `\%` 而非 `%`——用户输入 `%` 想找字面含 `%` 的行反而**漏匹配**（离线实测：现状返回空，正确应返回 `100%done`）。转义与 ESCAPE 子句必须成对，缺一即错。
- **次要候选（F-01/F-02，核验登记）**：`compliance/checker.go:245` 黑名单条目无空串守卫（`strings.Contains(sourceCat, "")` 恒真，配置含空串即该站全部种子被拒；同函数 `:305` 的 `catExcludes` 循环有 `if cat == "" { continue }`，明确不一致）；`extract_size.go:134` float→int64 极端值可能溢出为负（需异常大外部输入，概率低，标注未实测触发）。
- **正面结论**：盘点独立核验了正则捕获组索引、时间/时区、GORM 语义层、整数除法、循环 defer、uint 下溢、slice 别名等维度，均健康，不作主导。
- **明确不做**：改搜索业务语义、加输入黑名单（应转义而非禁字符）、碰靶机验证。

## 2. 重点发现

### V-01 · LIKE 通配符未转义——用户输入劫持搜索过滤（中危 · 查询语义）

- **级别**：中危（阅读档「中危」；CVSS 更适合功能语义缺陷，技术档记 `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N` 仅供参照）——认证用户可让搜索返回全表，破坏过滤语义；非注入、非崩溃。
- **证据**（正例 vs 反例对照）：

```go
// 正例1 declaration_backfill_task.go:38（有 likeEscape + ESCAPE 子句）
func likeEscape(s string) string {
    s = strings.ReplaceAll(s, `\`, `\\`)
    s = strings.ReplaceAll(s, `%`, `\%`)
    s = strings.ReplaceAll(s, `_`, `\_`)
    return s
}
esc := "%" + likeEscape(p) + "%"
"... LIKE ? ESCAPE '\\' ..."   // 转义 + ESCAPE 成对

// 正例2 site_handler_crud.go:30-32（NewReplacer + ESCAPE 子句）
escaped := strings.NewReplacer("%", "\\%", "_", "\\_").Replace(search)
"... LIKE ? OR domain LIKE ? ESCAPE '\\'"   // 注意：仅第二条带 ESCAPE

// 反例 seed_list.go:123/126（直接拼接，无转义）
searchArgs = []interface{}{"%" + q.search + "%", ...}  // q.search 来自 URL.Query().Get("search")
```

  未转义端点清单（均直接拼 `"%"+用户输入+"%"`）：`seed_list.go:123/126/236/239`、`publish_torrents_handler_seeddata.go:523`、`publish_torrents_handler_seed_detail.go:54`、`seeding_handler_records.go:100/347/350`、`reseed_handler.go:452/455`（`site`/`torrentID` 模糊筛选）、`publish/pipeline.go:477`。
- **影响**：任一认证接口的 `search`/`keyword`/`site` 参数传入 `%` 或 `_` 即命中全表，搜索框失去过滤作用；发布候选、种子列表、辅种记录、发布日志等高频页面均受影响。GORM 参数绑定防注入，但挡不住通配符语义劫持。
- **复现**（Python 内存 SQLite，伪种子名 5 行）：

```
用户输入 '%' 无转义: like='%%%' -> ['ProjectA','ProjectB','Foo_Bar','100%done','abc']   # 全命中
用户输入 '_' 无转义: like='%_%' -> ['ProjectA','ProjectB','Foo_Bar','100%done','abc']   # 全命中
用户输入 '%' 转义后: like='%\\%%' -> ['100%done']   # 正确：仅字面
用户输入 '_' 转义后: like='%\\_%' -> ['Foo_Bar']    # 正确：仅字面
```

  原始输出见 `evidence/like-wildcard-repro.txt`。
- **整改**：抽取**公共 LIKE 转义单点**（复用/提取 `likeEscape` 到公共包），所有用户输入拼接 LIKE 模式前统一转义；每条 `LIKE ?` 必须配 `ESCAPE '\'` 子句。禁止各端点手搓。注意转义顺序：`\` → `\\` 必须最先，否则二次转义出错。

### V-02 · 转义值缺 ESCAPE 子句——"正例"漏匹配字面通配符（中危 · 同型深层）

- **级别**：中危（转义与 ESCAPE 必须成对，缺一即语义反转）。
- **证据**（`ptgen_handler.go:83-84`）：

```go
escaped := strings.NewReplacer("%", "\\%", "_", "\\_").Replace(keyword)
q = q.Where("query_key LIKE ? OR chinese_title LIKE ?", "%"+escaped+"%", "%"+escaped+"%")
// 两条 LIKE 均无 ESCAPE '\' 子句
```

  对比正例1/正例2 都带 `ESCAPE '\\'`。SQLite/MySQL 默认无转义字符时 `\%` 是字面两字符，`LIKE '%\%%'` 匹配的是"含字面反斜杠+任意串+字面百分号"——字面 `%` 查询反而返回空。
- **影响**：PTGen 缓存搜索里想查字面含 `%` 或 `_` 的关键词（如标题含 `100%`）反而搜不到——与 V-01 症状相反但同源（转义与 ESCAPE 不成对）。`site_handler_crud.go:32` 也有类似隐患：`name LIKE ? OR domain LIKE ? ESCAPE '\\'` 仅第二条带 ESCAPE，第一条 `name LIKE ?` 缺子句。
- **复现**（内存 SQLite）：`pattern='%%\%%'` 时无 ESCAPE → `[]`，带 `ESCAPE '\'` → `['100%done']`。见证据文件。
- **整改**：所有带转义值的 `LIKE ?` 一律补 `ESCAPE '\'`；与 V-01 共用公共单点时把 ESCAPE 子句固化在 helper 产出的 SQL 片段里，杜绝遗漏。

### F-01 · 合规黑名单空串恒命中（低危 · 次要）

- **级别**：低危（配置错误触发，非代码必然路径）。
- **证据**（`compliance/checker.go:245`）：`if strings.Contains(sourceCat, blockedCat)`，`blockedCat` 来自 DB 配置 `compliance_site_blacklist`（`:350-375`），无空串守卫；`sourceCat != ""` 时 `Contains(x, "")` 恒真。同函数 `:305` 的 `catExcludes` 循环明确有 `if cat == "" { continue }`——一处有守卫一处没有，属明确不一致。
- **影响**：管理员误配含空串的黑名单条目 → 该站点全部种子被合规拒绝。
- **整改**：黑名单读取时过滤空串（与 `catExcludes` 同款守卫）；配置写入口校验拒空条目。

### F-02 · 外部尺寸 float→int64 溢出为负（低危 · 未实测触发）

- **级别**：低危（需异常大外部输入，概率低，标注「未实测触发」）。
- **证据**（`extract_size.go:11,134`）：`sizeValueRe` 用 `[\d.,]+` 不限位数，`int64(val * 1024^4)`；超大数值 `ParseFloat` 成功但转 `int64` 可能溢出为负。
- **整改**：转换前判 `val > math.MaxInt64/1024^4` 拒绝或钳位。本篇仅登记，不作主导。

### 正面结论：经核验健康的维度

独立复核确认无硬缺陷：正则捕获组索引（含 `FindAllStringSubmatchIndex` 点位守卫正确）、时间/时区（`.UTC().Format` cutoff 一致、`time.Parse` 三层兜底）、GORM 语义层（`ErrRecordNotFound` 判定、`Updates` 结构体零值、nil map 写入有守卫）、整数除法截断顺序、循环 defer（均 goroutine 内）、uint 减法、slice 截取别名（仅日志裁剪可忽略）。`extract_size.go:134` 的 `1024^4` 实为 `1024*1024*1024*1024`，非 Go 异或误写。

## 3. 整改建议

- **刀1（V-01）**：抽取公共 LIKE 转义单点（提取 `likeEscape` 到公共包，固化 `\`→`\\`→`%`→`\%`→`_`→`\_` 顺序 + `ESCAPE '\'` 子句），9+ 个搜索端点统一调用，删除各手搓拼接。
- **刀2（V-02）**：所有带转义值的 `LIKE ?` 补 `ESCAPE '\'`（`ptgen_handler.go:84` 两条、`site_handler_crud.go:32` 第一条）；公共单点把 ESCAPE 固化进 SQL 片段，杜绝漏配。
- **刀3（F-01/F-02 + 防回归锚）**：黑名单过滤空串 + 配置写入校验；尺寸转换前置上界钳位。新增查询语义锚——表驱动构造含 `%`/`_`/字面反斜杠的输入，断言转义后仅命中字面行（阴性对照：去掉转义 → 锚必须全命中，确认可触发）。
