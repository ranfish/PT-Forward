# 08 站点适配器复用治理

- **状态**：精读完成，整改方案待确认
- **日期**：2026-11-25
- **基线**：`ef7f246a`（`fix §59.568 刀1 补注+07 复审微瑕修正`）；提交前已 rebase 至 `218c5259`（v0.0.1613），期间上游重写 `adapter_hxpt.go`（全切 Token）并落地附录E §3 计数修正——本文涉及的 API 骨架、URL 基址、framework 清单事实已在新基线重核，仍成立。
- **审计范围**：`internal/adapter/` 生产代码（40 个生产文件、约 1.6 万行、12 个 adapter 结构体）及 `internal/model`/`internal/site`/`internal/publish` 中与框架标识、公共 helper 相关的调用面。
- **审计方法**：盘点 adapter 结构体与接口实现、factory 路由与框架默认值表、包内/跨包同名 helper、API 请求骨架、既有复用约定（`apihelper.go` 的「共享机制·不共享方言·三次法则」）；对疑似重复逐项读实现核实，区分「真重复」「方言差异」与「接口实现同名」三类。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。

## 1. 结论摘要

- adapter 包的复用底座**已经成型**，不是「一盘散沙」：`errors.go` 提供 `drainBody`/`readBody`/`networkError`/`parseError`，`adapter_nexusphp.go` 的 `setCommonHeaders` 被引用 105 次；`apihelper.go` 还成文写明「共享机制·不共享方言·三次法则后再升 util」。12 个结构体中有多个通过嵌入 `*GenericAdapter` 复用通用能力。因此本次**不建议大拆大合**。
- 12 个 adapter 各自实现的 `SearchTorrents`/`GetTorrentDetail` 等方法名相同，是 `model.SiteAdapter` 接口实现，**不是重复代码**——不纳入整改。
- 真正值得治理的是**「框架标识」这一概念的表示**：同一概念在七处各抄一份清单，彼此不校验且存在漂移；另有 `nexusphp`/`np` 两套词汇域混用。这是本次最实的问题（P2）。
- 经查 `docs/31`，部分「缺项」是**有意设计**（`FrameworkDefaults` 不注册 API-only 无 RSS 站），不是缺陷——这类边界必须写进规约，避免后来者误补。
- 代码层面能做的零行为变更收敛有限但明确：`baseURLOf` 与 `resolveBaseURL` 是同一逻辑两个名字；API 请求骨架在三到四个站点间重复，可下沉到既有机制层。**站点正则、方言字段映射、站方特化一律不动**；三套 URL 基址 helper 统一到 `siteBaseURL` 属行为变更，不在本轮。

## 2. 重点发现

### 2.1 框架标识七处手抄、互不校验且已漂移（P2）

**证据**：

「framework 有哪些合法取值」这件事，在代码、测试与前端里至少七处各自维护：

| 位置 | 形式 | 项数 | 覆盖情况 |
|---|---|---|---|
| `internal/adapter/factory.go` `Factory.Create` | switch | 13 | nexusphp/tnode/yemapt/mteam/cola/piggo/hdarea/hxpt/unit3d/gazelle/rousi/luminance + default 兜 generic |
| `internal/adapter/factory.go` `FrameworkDefaults` | map | 10 | 上述 8 项 + cola/yemapt/rousi；hdarea/hxpt/piggo 未注册（见下，属有意设计） |
| `internal/model/config_types.go` `FrameworkLabels` + 常量 | map + 8 个常量 | 8 | nexusphp/unit3d/gazelle/mteam/tnode/luminance/rousi/generic |
| `internal/model/model_test.go:335` `frameworks` | 测试内手抄切片 | 8 | 与上表完全相同 |
| `internal/adapter/factory_test.go:25` `expected` | 测试内手抄切片 | 6 | nexusphp/unit3d/gazelle/mteam/luminance/generic |
| `internal/adapter/factory_test.go:58` `cases` | 测试内手抄表 | 6 | tnode/mteam/unit3d/gazelle/rousi/luminance |
| `web/src/views/sites/SiteDetail.vue:447` `frameworkLabels` | 前端手抄 map | 11 | 上述 8 项 + cola/hdarea/hxpt；**缺 piggo、yemapt** |

已观测到的具体漂移与边界：

- `model.FrameworkLabels` / `ValidFramework` 不认识 `cola`、`yemapt`、`piggo`、`hdarea`、`hxpt`，但这五个在 `Factory.Create` 里都有真实分支；前端标签则缺 `piggo`、`yemapt`。
- `ValidFramework` 与 `FrameworkLabels` 在全仓**仅被 `model_test.go` 引用**，生产代码零调用；`FrameworkNexusPHP` 等 8 个类型常量在生产代码也零引用（生产一律用裸字符串）。这是一座「只跟自己的测试对话」的孤岛。
- `TestFrameworkLabels_Completeness` 用测试内手抄的 8 项清单做完整性断言，因此**检测不到与 factory 真实集合的漂移**；`TestFrameworkDefaults_ContainsAll` 只断言 6 项，同样覆盖不全。
- **反例（不是缺陷）**：查 `docs/31` §59.533 刀2 与附三，`FrameworkDefaults` 不注册 hdarea/hxpt 是「API-only 无 RSS 站不进（HashStrategy 等字段全 RSS 消费）」的明确设计；piggo 则由 migration173 在站点行上直接写 `hash_strategy=fake_from_id`/`id_strategy=path_segment` 覆盖。这三处空白不应机械补齐，但代码里没有就地注释说明，容易被误判为遗漏。

**风险**：

- 新增一个 framework 时需要改多处、且没有强制检查，漏改不会让任何测试变红（前端标签漏 piggo/yemapt 已是现成例子）。
- 测试里的「完整性」断言基准是手抄子集，给出虚假的安全感。

**建议**：

- 先做规约（附录G）：明确 framework 标识的权威来源与各消费点、新增框架时的更新清单，并**写明 `FrameworkDefaults` 的有意不注册规则**。
- 补全 `FrameworkLabels`/常量至 factory 全集，并把完整性测试的基准改为单一来源（而非测试内手抄）——此项不改变生产行为，因生产零调用。
- 前端标签缺项属展示层文案，改动需走前端构建流程，单独评估。

### 2.2 同一概念两套词汇域：`nexusphp` 与 `np`（P2）

**证据**：

- `sites.framework`（adapter 路由域）使用 `"nexusphp"`，生产代码 92 处；`Factory.Create` 只认 `"nexusphp"`，没有 `"np"` 分支。
- `PublishFormConfig.Framework`（发布表单生成域）中，`"np"` 出现 74 次（主要在 migration 的表单配置 JSON、`form_config_diff.go:119` 的草稿默认值），同时也有 4 处写成 `"nexusphp"`。
- `internal/publish/executor_stages.go` 同时读两个域：`site.Framework == "tnode"` 与 `cfg.Framework == "piggo"`，但没有 `np`↔`nexusphp` 的归一化函数（全仓搜索无 `case "np"` 或别名映射）。
- 两者在各自域内目前能跑通，但「同一个站、同一个框架概念、两种写法」没有成文边界。

**风险**：跨边界传递 framework 值时，若把表单域的 `"np"` 直接送进 `Factory.Create`，会落入 default 分支得到 `GenericAdapter("np")`，而不是 `NexusPHPAdapter`——表现是站点能力静默降级。当前调用链未发现这样的直传，属于潜在风险而非已发生缺陷。

**建议**：在附录G 中明确两个词汇域的边界与取值表；如未来需要跨边界转换，收敛到一个显式归一化函数，而不是在各处散写字符串比较。

### 2.3 URL 基址三套 helper，其中两套完全同义（P3）

**证据**：

| helper | 位置 | 语义 | 消费面 |
|---|---|---|---|
| `siteBaseURL` | `errors.go:142` | `BaseURL` 优先（去尾斜杠）→ `Domain` 含协议直用 → 裸域补 `https://` | hdarea/hdcity/hxpt/nexusphp_edit/piggo 五处；`docs/31` §59.533 附明确定义为公共单点（收编 hdcity 既有防御） |
| `resolveBaseURL` | `adapter_mteam_upload.go:276` | `BaseURL` 非空取之，否则裸取 `Domain`（无补协议/去斜杠） | gazelle/cola/mteam；§59.460 为可乐三面分离站引入 |
| `baseURLOf` | `adapter_generic.go:676` | 与 `resolveBaseURL` **完全相同** | generic/nexusphp_upload（喂给自带补协议的 `BuildNexusDownloadURL`） |

- `baseURLOf` 与 `resolveBaseURL` 是同一逻辑两个名字，零行为差异。
- `siteBaseURL` 语义更强（补协议/去尾斜杠），但 `resolveBaseURL`/`baseURLOf` 的调用点未采用它——这属于历史分层，不是简单重复。

**风险**：`baseURLOf`/`resolveBaseURL` 重复实现，后续任一处修正容易漏改另一处；三套并存也增加「该用哪个」的认知成本。

**建议**：

- 零行为变更刀次内：让 `baseURLOf` 委托 `resolveBaseURL`，保留可乐说明注释。
- **不把 `resolveBaseURL`/`baseURLOf` 改成 `siteBaseURL`**——后者会为裸 `Domain` 补 `https://`、并去尾斜杠，属行为变更，需单独评估（且 `BuildNexusDownloadURL` 已有自己的补协议逻辑）。

### 2.4 API 请求骨架三到四处重复，可下沉到既有机制层（P3）

**证据**：

- `detailViaAPI`：`adapter_gazelle.go:164`、`adapter_mteam_detail.go:14`、`adapter_unit3d.go:212`。
- `slViaAPI`：`adapter_gazelle.go:552`、`adapter_mteam_slhr.go:499`、`adapter_unit3d.go:524`。
- `fetchUserStatsAPI`：`adapter_gazelle.go`、`adapter_mteam_upload.go`、`adapter_nexusphp_userstats.go`、`adapter_unit3d.go` 共 4 处。
- 这些方法的 HTTP 骨架一致：`http.NewRequestWithContext` → 设头 → `a.doer.Client.Do` → `defer drainBody(resp)` → `readBody(resp)` → JSON 解析；差异全在方法/URL/请求头/响应结构（方言）。
- 机制层已有 `errors.go` 的 `drainBody`/`readBody`/`networkError`/`parseError` 与 `setCommonHeaders`，骨架部分下沉有现成落点。

**风险**：重复的骨架本身不致错，但错误包装口径已有细微差异（有的用 `networkError`/`parseError`，有的直接返回原始 err），后续统一错误处理时容易漏改。

**建议**：**不强行合并整个方法**，只考虑把 `Do → drainBody → readBody → Unmarshal → parseError` 这段纯机制抽成一个 helper，请求构造与响应结构保留在方言层——完全符合 `apihelper.go` 的既有铁律。落地前需逐点核对错误包装等价性；若核对成本高于收益，则只在附录G 里记为规约，不动代码。

### 2.5 跨包同语义小 helper（P3，渐进）

**证据**：

- `adapter_yemapt.go:564` `extractDoubanID` 与 `publish/executor_helpers.go:107` `extractDoubanID` 同名，实现不同（前者委托 `extractNumericID`，后者正则 + 纯数字兜底），语义相近但不确定等价。
- `publish/gpw_inject.go:251` 的 `gpwFirst` 注释明确写着「adapter 层 `firstNonEmpty` 同语义」，属于已知但未提取的重复。
- adapter 包内有 160 个包内私有小函数，分布在 29 个文件——数量本身不是问题，但说明「小工具散落」是常态。

**风险**：低。当前未发现因这些 helper 产生的不一致。

**建议**：遵守既有「三次法则」——出现包外消费者或第三站证明流程稳定时再升公共 util；现阶段仅在附录G 记录现状，不机械搬迁。

### 2.6 正面结论：不应被误判为问题的部分

- **接口实现同名不算重复**：12 个 adapter 的 `SearchTorrents`/`GetTorrentDetail`/`Framework` 等方法同名，是 `model.SiteAdapter` 接口的实现，属于必要结构。
- **机制层已成型**：`setCommonHeaders` 105 处、`drainBody` 130 处、`readBody` 103 处引用，说明公共 HTTP 机制早有收敛，不必重建。
- **嵌入复用已在用**：`ColaAdapter`/`Unit3DAdapter` 等嵌入 `*GenericAdapter`，是合理的复用形态。
- **`adapter/apihelper.go` 已有成文边界**：「共享机制·不共享方言」「包内私有·三次法则后再升 util」。本次治理沿用该约定，不另立标准。

## 3. 整改建议

按零行为变更、逐刀验证的节奏，建议如下（均需确认后再动）：

- **刀1（纯文档）**：新增附录G「站点适配器复用边界与框架标识规约」，固化 2.1/2.2 的事实表、七处清单、`FrameworkDefaults` 有意不注册规则与迁移规则。（附录E §3 计数修正已由上游 `5248c035` 落地，不重复做。）
- **刀2（零行为变更代码）**：`baseURLOf` 委托 `resolveBaseURL`（2.3），并补一处注释说明两者同义。
- **刀3（待单独确认）**：补全 `FrameworkLabels`/常量并把完整性测试改为单一来源（2.1）——生产零调用，但会改变测试可见 API 的返回值集合，需确认后做。
- **不做（需专项授权）**：三套 URL 基址统一到 `siteBaseURL`、API 骨架下沉若涉及错误包装差异修正（均为行为变更）；前端 frameworkLabels 补项（需走前端构建）；任何站点正则/方言字段/站方特化改动。`FrameworkDefaults` 的 hdarea/hxpt/piggo 空白是设计决策，**不补**。

## 4. 验证建议

- 每刀后跑 `go test -count=1 ./internal/adapter/... ./internal/model/... ./internal/site/...`。
- 刀2 额外对照 `resolveBaseURL` 与 `baseURLOf` 的输入输出（空 `BaseURL`、非空 `BaseURL`）确保等价；可用一个临时表驱动测试验证后删除或保留为回归锚。
- 全量 `go test ./internal/...` 在收口时跑一次；仓库前端 `dist` 未构建会导致 `go build ./...` 报 `frontend/spa.go:11 no matching files found`，属环境问题，非本系列改动引入。

## 5. 本次未覆盖

- 各站点 HTML 正则、字段映射字典、发布表单方言配置的正确性（站方语义，非复用治理范畴）。
- `publish`/`api` 包 Deep 复用（本次仅触及与 adapter 交界的 helper 与 framework 比较）。
- 62 个站点的实际数据分布（framework 取值来自运行时 DB，本文只审代码中的枚举与消费逻辑）。
- HTTP 边界资源治理（响应体关闭、超时重试口径）——留作独立方向。

## 6. 后续方向

- 若刀3 落地后漂移问题仍未根治，可评估将 framework 注册表统一到一处（如 `model` 定义、adapter 引用），但这跨包且影响面大，需单独评估。
- HTTP 边界资源治理（`client.Do`/`Body.Close` 口径）与发布链状态机审计仍是可继续的方向。
