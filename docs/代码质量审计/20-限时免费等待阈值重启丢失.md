## 1. 结论摘要

- 本篇是第 20 篇，由三路盘点据实立项（非预设）。已登记两候选（`screenshot.go` 临时目录清理死代码、字幕选轨虚锚）经复核仍在但证据偏薄；全库正交面扫描找到一条更强方向：`FreeWaitMonitor` 的 `MinRemainMin` 只活在内存里，重启即丢。
- **V-01（中危·功能缺陷非漏洞）**：设计 `docs/31:65897-65900`（P2 `FreeWaitMinRemain` 可行性检查，v0.0.526）明定「免费后检查剩余时间，短于阈值则跳过并移出队列，防止推了下载不完的种子」。`Add` 把阈值写入内存 entry（`:118`），但 DB 模型 `model.FreeWaitEntry` 无此字段（`:5-21`）、`dbEntry` 构造也无此键（`:121-137`）；`RecoverOnStartup`（`:51-76`）从 DB 重建时自然归零；`CheckOnce`（`:210-224`）的 `e.MinRemainMin > 0` 闸门恒假，保护整段跳过。离线复现实锤：未重启 5 分钟剩余正确跳过（pushed=0）；模拟重启后同一场景 `MinRemainMin 30→0`、`pushed=1`。
- **同族漏网定性**：同一设计段落的 P1（`RecheckSec`/`LastCheckAt`）完整做了「运行时字段 ↔ DB 字段」配对，`Add` 写、`RecoverOnStartup` 读；P2 加 `MinRemainMin` 时漏了配对这一步。这不是「项目没有持久化纪律」，而是新加的保护字段漏接既有纪律——与 19 篇 `discountCache` 漏接站点维度同型（不同主题）。
- **诚实边界**：保护失效需要「进程重启」+「重启后恰好命中剩余时间短于阈值的免费种子」两条件叠加，其真实发生频率未取证；未宣称发生过生产事故。默认值 30 来自 `model/rss.go:135` 的 `gorm:"default:30"`，设计 P2 只规定机制未规定取值。
- **明确不做**：不改生产代码、不碰靶机、不改业务语义；本篇只做精读与整改建议，修复另案。

## 2. 重点发现

### V-01 · `MinRemainMin` 未持久化，重启后「剩余过短跳过」保护静默失效（中危 · 内存态→DB 模型字段漂移）

- **级别**：技术档 CVSS v3.1 `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N` ≈ **4.3（低）**——仅作阅读辅助；**不是安全边界漏洞**（无越权、无数据泄露、无 DoS）。阅读档 **中危**：这是确凿的业务规则失真，触发路径生产可达（升级/发布/崩溃恢复必然重启），后果是用户拿到下载不完的限时免费种子，直接违背该功能的存在目的；按业务上下文上调阅读档位。
- **证据**（`internal/model/free_wait.go:5-21`、`internal/seeding/free_wait.go:51-76,86-137,205-224`、`internal/model/rss.go:135`、`internal/seeding/engine_stats.go:262`、`internal/seeding/engine.go:258`，基线 `cba999b3`）：

```go
// model/free_wait.go:5-21 —— DB 模型字段止于 RecheckSec/CheckBefore/CheckCount/LastCheckAt，无 MinRemainMin
type FreeWaitEntry struct {
    ...
    HasHR          bool
    HRSeedTimeH    int
    CheckBefore    *time.Time
    CheckCount     int        `gorm:"default:0"`
    RecheckSec     int        `gorm:"default:600"`
    LastCheckAt    *time.Time `gorm:"index"`
}

// seeding/free_wait.go:118 —— 内存侧写入阈值
entry := &freeWaitEntry{ ... MinRemainMin: minRemainMin }
m.pending[key] = entry

// seeding/free_wait.go:121-137 —— 构造 DB 记录时无处可写（model 无此字段）
dbEntry := &model.FreeWaitEntry{ ... RecheckSec: recheckSec, LastCheckAt: &now }
m.db.Create(dbEntry)

// seeding/free_wait.go:58-71 —— 重启恢复：逐字段重建，无 MinRemainMin → 零值
m.pending[key] = &freeWaitEntry{
    ... RecheckInterval: time.Duration(dbEntry.RecheckSec) * time.Second,
    // MinRemainMin 未赋值 → 0
}

// seeding/free_wait.go:210-224 —— 保护闸门：阈值归零即整段跳过
if freeEndAt != nil && e.MinRemainMin > 0 {
    remaining := time.Until(*freeEndAt)
    if remaining < time.Duration(e.MinRemainMin)*time.Minute {
        m.Remove(e.SiteName, e.TorrentID); continue   // 跳过并移出队列
    }
}
if addFunc != nil { _ = addFunc(ctx, e) }              // 归零后直接走到这里推送
```

- **设计权威**（`docs/31-模块设计决策记录.md:65897-65900`，P2 `FreeWaitMinRemain 可行性检查` v0.0.526 原文）：

> `CheckOnce` 在种子变免费后检查剩余时间：`freeEndAt != nil && MinRemainMin > 0 && time.Until(*freeEndAt) < MinRemainMin * time.Minute` → 跳过并移出队列。永久免费（`FreeEndAt == nil`）或 `MinRemainMin == 0` → 跳过检查，直接推。

  P2 明确把 `MinRemainMin == 0` 语义定义为「不检查、直接推」——恢复归零后恰好落入这个分支，所以不是「检查失效报错」，而是**静默地按「用户没设保护」处理**。P3（`:65902-65904`）的展示字段 `minRemainMin` 重启后也会显示 0，是唯一可观察信号。
- **触达路径**：订阅开启 `free_wait_enabled` → `FreeWaitMinRemain`（默认 30，`model/rss.go:135`）→ `engine_stats.go:262` 调 `Add(..., sub.FreeWaitMinRemain)` → 内存 pending 持有阈值 → **进程重启**（升级/发布/崩溃恢复，`engine.go:258` 调 `RecoverOnStartup`）→ 阈值归零 → 下次 `CheckOnce` 检测到免费且 `freeEndAt` 仅剩数分钟时，`e.MinRemainMin > 0` 为假 → 直接 `addFunc` 推送 → 用户拿到下载不完的种子。
- **复现**（包内临时测试 `internal/seeding/zz_repro20_test.go`，直接调生产 `Add`/`RecoverOnStartup`/`CheckOnce`，取证后即删，完整输出见证据文件）：

  场景 A（未重启）阈值 30、剩余 5 分钟 → 条目被 `Remove`、不推送；场景 B（新建 monitor 从同一 DB `RecoverOnStartup`，模拟重启）阈值归零 → 同一 5 分钟剩余被推送。两态共用同一 checker 与 `addFunc` 形态，唯一变量是「是否经过 DB 恢复」。

### F-01 · 触发频率与归因边界（信息 · 登记不主张）

- 保护失效需要两条件叠加：①进程重启；②重启后队列里恰好有「变免费且剩余时间短于阈值」的种子。二者是否在生产中同时发生过，未取日志证据；结论限定为「代码路径确凿 + 离线复现实锤」，不宣称生产事故。
- 默认值 30 来自 `model/rss.go:135` 的 `gorm:"default:30"`；设计 P2 只规定检查机制，未规定默认取值，本篇不评价取值本身是否合适。
- 存量 pending 行的回填策略（AutoMigrate 加列后旧行填默认值 vs migration 从订阅配置回填）属实施决策，本篇给出建议不替业主裁决，见 §3 刀1 的诚实说明。

### 正面结论：经核验健康、不主张的维度

- **同族正例 P1**（设计 `docs/31:65889-65896` v0.0.525）：`RecheckSec`/`LastCheckAt` 完整配对——`Add` 同时写内存 `RecheckInterval`/`LastCheckAt` 与 DB `RecheckSec`/`LastCheckAt`（`:120,135-136`），`RecoverOnStartup` 读回并换算（`:69-73`）、还原 `CheckBefore`/`CheckCount`/`LastCheckAt`。证明「运行时字段须进 DB」是设计既有纪律，V-01 是 P2 加字段时漏接。
- **同包正例 `free_end.go:192-240`**：`FreeEnd` 队列的恢复直接把完整 `SeedingTorrentRecord` 模型放进内存，天然无字段漂移——反证 `free_wait` 的漂移是该队列特有，不是框架性问题。
- **测试盲区定性**：`free_wait_test.go:150-163` 的 `TestFreeWaitMonitor_RecoverOnStartup` 只断言 `PendingCount()`，不查字段保真——不是写了假断言，而是覆盖维度缺失（只验「条数回来了」，没验「字段回来了」）。这正是 §3 刀2 端到端锚要补的维度。
- **持久化机制**：生产表由 `internal/model/migrate.go:61` 的 `AllModels()` 统一 `AutoMigrate`（含 `&FreeWaitEntry{}`）；加字段走 model 结构变更即可由 AutoMigrate 补列，无需手写 migration 文件（存量回填语义见 §3）。

## 3. 整改建议

> 以下为精读提出的三刀建议，**尚未实施**；待业主修复后按约定复审（复审须做三阴性对照 + 端到端锚实跑 + 全量验证比对基线）。

- **刀1（V-01 根修·字段配对）**：① `model.FreeWaitEntry` 增 `MinRemainMin int ` + `gorm:"default:30"`，与 `model/rss.go:135` 的配置默认值一致；② `Add` 构造 `dbEntry` 时写入 `MinRemainMin: minRemainMin`（内存侧已有，补 DB 侧）；③ `RecoverOnStartup` 重建内存 entry 时从 `dbEntry.MinRemainMin` 回填。三处必须同批改，缺任一处则恢复仍归零。**存量行诚实说明**：AutoMigrate 加列后旧行由 `default:30` 填 30，与配置默认一致；用户若把 `free_wait_min_remain` 改成非 30，存量行的真实入队阈值已不可追回（当初就没存），统一填 30 是合理近似，须在 docs/31 §59.593 记录该边界；若业主要求存量按当前配置回填，另加一次性 migration 从订阅配置读取（属可选增强，不并入本刀）。
- **刀2（防回归锚）**：① 模型字段锚——断言 `model.FreeWaitEntry` 的 GORM schema 含 `MinRemainMin`（防字段被删）；② 端到端锚——`Add(..., minRemainMin=30)` → 新 monitor 对同一 DB `RecoverOnStartup` → 断言恢复后 `MinRemainMin==30` 且 `CheckOnce` 对 5 分钟剩余 `pushed=0`，直接复刻本次复现形态，直调生产方法不 mock，专补 `TestFreeWaitMonitor_RecoverOnStartup` 缺的字段保真维度；③ 静态锚——扫描 `Add` 的 `dbEntry` 构造块与 `RecoverOnStartup` 的 `freeWaitEntry` 构造块都必须出现 `MinRemainMin`，点名文件行号（沿 16/17/18/19 篇静态锚惯例：仓库根 Walk + 一级目录白名单 + 注释截断 + 测试豁免）。
- **刀3（三阴性对照）**：A 从 model 删 `MinRemainMin` → 模型字段锚 + 端到端锚 FAIL；B 只改 model + `Add` 写入、不补 `RecoverOnStartup` 回填（半成品修复）→ 端到端锚 FAIL（阈值仍归零）；C 静态注入删掉 `dbEntry` 写入行或 `RecoverOnStartup` 回填行 → 静态锚点名 FAIL。三阴性须逐条注入→锚红→恢复→工作区干净（08 篇方法论：声明逐条可触发验证，杜绝虚拟安全感）。
