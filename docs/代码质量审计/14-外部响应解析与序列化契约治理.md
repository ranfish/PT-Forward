- **状态**：精读完成，整改建议待实施
- **日期**：2026-11-27
- **基线**：`32145be3`（13 三刀 + 补刀落地后，`origin/main` 最新）
- **审计范围**：「外部数据形态与 Go 结构体契约的匹配性」——入站看外部 API 响应 JSON 的数值形态能否被解析结构体正确接住，出站看响应序列化时零值字段是否按契约存在；并核验静默默认值语义与第二套换算实现的漏网。
- **审计方法**：全库盘点 1055 个生产 Go 文件、避开 01-13 覆盖维度后据实立项（非预设）；按方向批量 grep 定位 → 逐个精读核验 → 用真实 `encoding/json` 与真实 `flexInt` 本地离线复现（不请求真实站点）；对照 03/04/11/13 划清正交边界；对盘点中核验健康的维度（atomic、sync.Once、类型断言、错误包装、SQL 非 LIKE 拼接、分页、TTL、retry）独立复核确认健康。
- **证据文件**：`evidence/tool-versions.txt`（工具版本+基线）、`evidence/response-contract-repro.txt`（两段离线复现真实输出 + 形态来源摘录）。

## 1. 结论摘要

- 本篇是全库盘点后新立的独立方向。13 篇高强度审计后，盘点未发现「未被覆盖 + 可离线复现 + 确凿功能性硬缺陷」三者兼备的新方向； 最有力的证据集中在**数据形态契约**：外部响应的数值形态与解析结构体不匹配（入站），以及响应序列化时零值字段消失（出站）。与前序篇正交：03 管错误日志、04 管请求入参/分页/错误码、08 管站点适配器复用、11/13 管整数溢出与尺寸上界——本篇管「形态契约对不对」。
- **确认一处确凿功能性缺陷（V-01，中危）**：`adapter_unit3d.go:849-852` 的 `/api/user` 响应把 `uploaded`/`downloaded` 声明为 `flexInt`、`ratio`/`seedbonus` 声明为 `float64`，而 `docs/34-UNIT3D-API完整指南.md:344-347` 记录的真实响应形态是 `"uploaded": "50.00 GiB"`、`"ratio": "50.00"` 这类带单位字符串与字符串数值。离线实测：整体解析报 `json: cannot unmarshal string into Go struct field .ratio of type float64`，`uploaded` 单独测则无错归零。`FetchUserStats`（`:803-809`）在 API 失败时**直接返回错误、无 HTML 降级**——配置 APIKey 的 UNIT3D 站点用户统计整体不可用。
- **确认一处契约失真（V-02，低危·当前无功能损坏）**：`site/supported.go:42` `PublishSupported bool json:"publish_supported,omitempty"`——同一结构体的 8 个布尔位全部用 `*bool + omitempty`（明确区分 false 与未设置），唯独这一位用值类型；`false` 时键从 JSON 中整体消失。前端 `web/src/api/types.ts:284` 声明 `publishSupported: boolean`（非 optional），契约撒谎。当前前端是 falsy 消费（`SiteList.vue:89/93`、`SiteDetail.vue:309`），**暂无功能性错误**——定位为契约治理，不冒称硬缺陷。
- **次要候选（F-01/F-02）**：`flexInt.UnmarshalJSON`（`adapter_mteam.go:33-57`）解析失败吞错归零（现有测试固化了该行为，但 API 契约场景不适用）；`stats_helper.go:26-64` 是 13 篇 F-02 治理之外的**第二套独立字节换算**，含多小数点吸收（`"1.2.3"` → `1.23`）与裸 `int64(f*multiplier)` 上界漏网。
- **正面结论**：盘点独立核验 atomic/sync.Once/类型断言/错误链/SQL 非 LIKE 拼接/分页/`strings.Index -1`/TTL/retry_transport 等维度均健康，不作主导。
- **明确不做**：请求真实站点验证形态、改搜索业务语义、碰靶机。

## 2. 重点发现

### V-01 · UNIT3D `/api/user` 响应形态与解析结构体契约不匹配（中危 · 入站契约）

- **级别**：中危（阅读档「中危」；技术档参照 `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:L`）。上游响应形态偏离即导致自身统计功能整体失败；无数据损坏、无越权。
- **证据**：

```go
// adapter_unit3d.go:849-852（解析结构体）
var raw struct {
    ID         flexInt `json:"id"`
    Username   string  `json:"username"`
    Uploaded   flexInt `json:"uploaded"`
    Downloaded flexInt `json:"downloaded"`
    Ratio      float64 `json:"ratio"`
    Seedbonus  float64 `json:"seedbonus"`
    ...
}

// docs/34-UNIT3D-API完整指南.md:344-347（摸站记录的真实响应形态）
{ "username": "string", "uploaded": "50.00 GiB", "downloaded": "1.00 GiB",
  "ratio": "50.00", "seedbonus": "100.00", "seeding": 0 }
```

  `flexInt.UnmarshalJSON`（`adapter_mteam.go:33-57`）只接受纯数字或纯数字字符串：`ParseInt("50.00 GiB", 10, 64)` 失败 → `*f = 0; return nil`（静默归零）；`float64` 接 `"50.00"` 直接报 unmarshal 错误。

  `FetchUserStats`（`:803-809`）：`APIKey/BearerToken` 非空时只走 API 路径，失败即 `return nil, err`，**没有回退 HTML 路径**（HTML 路径 `:875` 存在 `reUnit3DUploaded` 等带单位解析能力）。
- **影响**：配置 APIKey 的 UNIT3D 站点用户统计（上传/下载/分享率/积分/做种数）整体失败；即使上游只把 `ratio` 改成字符串而数值形态保持数字，整体解析也失败。若上游响应里 `ratio` 是数字而只有 `uploaded` 是带单位字符串，则整体解析成功但上传/下载量静默显示为 0——两种失效路径都成立，取决于实际响应。
- **复现**（本地真实 `encoding/json` + 真实 `flexInt`，见证据文件）：

```
整体解析: err=json: cannot unmarshal string into Go struct field .ratio of type float64
          uploaded=0 downloaded=0 ratio=0.00 bonus=0.00
单字段 uploaded: err=<nil> value=0（静默归零）
```

- **形态来源可信度**：`docs/34` 是摸站记录（同文档 `:120-122` 另有数字形态的 torrent 列表样例，说明该站点族不同端点形态不一），本项目代码里**没有 `/api/user` 的 mock 测试或 docs31 实测记录**——形态证据止于文档记录，需实施前用真实站点响应闭环确认（本审计不请求真实站点）。
- **整改**：`/api/user` 响应结构体按 docs/34 形态修正——`uploaded`/`downloaded` 用带单位数值解析（复用 `parseSizeStr`/`sizeToBytes` 体系并做统一单点），`ratio`/`seedbonus` 用 `json.Number` 或自定义 `flexFloat` 双兼容字符串/数字；同时为 API 失败补 HTML 降级或明确标注"不降级"的设计理由。新增契约锚：以 docs/34 形态构造 JSON，断言解析结果非零且无 err。

### V-02 · `omitempty` 零值丢字段——出站契约失真（低危 · 契约治理）

- **级别**：低危（当前前端 falsy 消费无功能损坏；但类型契约失真，后续消费方按声明取值会拿到 `undefined`）。
- **证据**：

```go
// site/supported.go:28-42
ShowCookie      *bool `json:"show_cookie,omitempty"`      // 正例：false 仍输出
...
PublishSupported bool `json:"publish_supported,omitempty"` // 反例：false 时键消失

// web/src/api/types.ts:284
publishSupported: boolean   // 非 optional，与后端实际输出不符
```

  本地真实 `json.Marshal` 实测（`false` 两字段）：`{"show_cookie":false}`——`publish_supported` 完全消失；`true` 两字段：`{"show_cookie":true,"publish_supported":true}`。
- **影响**：`publish_supported=false` 的站点（绝大多数）在 API 响应里没有该键。当前前端 `SiteList.vue:89/93`、`SiteDetail.vue:309` 均用 falsy 判断，行为碰巧正确；但契约与声明不符，任何按 `boolean` 类型做严格校验（如 zod / TS runtime check）的新消费方都会失败。
- **同型实例**（响应/配置结构体，值类型 + omitempty 且零值有意义）：`model/torrent.go:24-32`（`LogScore`/`HasLog`/`HasCue`/`IsVanityHouse`/`IsScene`——注释明确"双 false → 转载可转"的 R7 判定依赖该位）、`model/publish_form_config.go:26/32/37`（`Anonymous`/`Offer`/`DescrQuoteOnly`）、`model/site.go:173/365/367/370`（`BrowserFallback`/`FetchRPS`/`DownloadHourlyLimit`）。请求体里的 `omitempty`（`site_handler_search_download.go`、`rss_handler.go`、`notify_handler.go`）零值等同未设置，属合理用法，**不在治理范围**。
- **整改**：响应结构体中"false/0 有意义"的字段改 `*bool`/`*int` 或去掉 `omitempty`，使键恒定存在；前端类型声明与本端保持一致。优先处理 `PublishSupported` 与 Gazelle 扩展位（有判定依赖），其余按消费方逐一确认后收敛。新增序列化锚：构造零值响应结构体，`json.Marshal` 后断言关键键存在且值为 false/0。

### F-01 · `flexInt` 静默吞解析错误（低危 · 解析默认值语义）

- **证据**（`adapter_mteam.go:33-57`）：字符串分支 `ParseInt` 失败返回 `nil` + 归零；数字分支 `json.Unmarshal(data, &n)` 失败同样归零；空串/空白也归零。现有测试 `adapter_tnode_mteam_test.go:1044-1065` 把 `"abc"`/`""`/空白 → 0 固化为预期行为。
- **影响**：`flexInt` 被 M-Team/Cola/UNIT3D 多站复用（`adapter_mteam_detail.go:41/56`、`adapter_cola.go:263/305`、`adapter_unit3d.go:849-852` 等），契约外的数值形态一律静默变 0，无法区分"真 0"与"解析失败"。这是有意容错的取舍，但用在 API 结构化响应契约上会把形态漂移伪装成合法零值。
- **整改**：区分容错场景与契约场景——站点页面文本抓取可保留归零；API 响应解析应返回 err 或记录告警，让 V-01 的失败显性化。

### F-02 · 第二套字节换算的多小数点吸收与上界漏网（低危 · 与 13 篇 F-02 同型）

- **证据**（`adapter/stats_helper.go:26-64`）：这是独立于 13 篇治理对象（`extract_size.go:parseSizeToBytes`）的第二套实现。
  - 多小数点：`val[strings.Index(val, ".")+1:]` 取第一个点之后的全部字符遍历，`"1.2.3"` 被吸收为 `1.23`（第二个点被跳过、第三位继续按更小权重累加），而正则 `([\d.]+)` 允许多点。属非溢出的语义错误。
  - 上界：`return int64(f * multiplier)` 无 13 篇 F-02 那种前置上界守卫，超大外部文本溢出为负（**与 13 篇 F-02 同型，属已覆盖维度的延伸治理，不重复主张为新发现**）。
- **影响**：M-Team 统计的 `uploaded`/`downloaded` 数值可能错误或为负。
- **整改**：把两套字节换算收敛到单一公共单点（13 篇已治理的 `parseSizeToBytes` 可直接复用或抽取公共包），同时修掉多小数点吸收逻辑（多点输入应判无效）。

### 正面结论：经核验健康的维度

独立复核确认无硬缺陷：atomic 全部为类型化 API（`atomic.Bool/Int64/Uint64/Value/Pointer`，`atomic.Value.Store` 类型一致）；sync.Once 均为 embed 资源懒加载；类型断言均有 ok/nil 守卫；错误链 `%w`/哨兵使用正确（用 `%v` 处均为 panic/超时值而非包装 error）；SQL 非 LIKE 拼接走 `switch` 白名单；分页 `parsePaginationWith` 保证 page≥1、size 1..200，内存分页有越界守卫；`strings.Index` 返回 -1 均有 `<0` 守卫；TTL 统一 `expires_at > now`/`Before(expiry)`；retry_transport 429 不重试、仅 5xx 重试、body 重放与 MaxDelay clamp 齐备。

## 3. 整改建议

- **刀1（V-01）**：按 docs/34 形态重写 `/api/user` 解析结构体（`uploaded`/`downloaded` 走带单位解析单点；`ratio`/`seedbonus` 走 `json.Number`/`flexFloat` 双兼容）；补 API 失败降级 HTML 或记录明确设计理由；新增 docs/34 形态契约锚（真实 JSON 字面量 → 断言非零无 err）。
- **刀2（V-02）**：响应结构体零值有意义字段改为指针或去 `omitempty`（优先 `PublishSupported` 与 Gazelle 扩展位），前端类型对齐；新增序列化锚（零值 marshal 后断言键存在）。
- **刀3（F-01/F-02 + 三层锚）**：`flexInt` 契约场景返回 err/告警；两套字节换算收敛公共单点并修多小数点；静态锚登记"响应结构体零值语义"与"外部响应解析形态"两类纪律（登记须附调用方/形态来源核验，沿用 13 补刀教训）。新增锚阴性对照：形态锚改回旧结构体须 FAIL、序列化锚恢复 `omitempty` 须 FAIL、静态锚删单点调用须 FAIL。
