- **审计范围**：`internal/` 生产代码中的超时、重试、批大小、并发、缓冲区、TTL、阈值、轮询间隔、默认值与配置来源；重点关注 `config`、`setting`、`httpclient`、`pusher`、`download`、`scheduler`、`watcher`、`reseed`、`api` 等高频编排/网络路径。

## 1. 结论摘要

- 配置来源呈 **三层分裂**：启动配置（YAML/env，`internal/config`）、运行时 DB 设置（`internal/setting`）、以及大量代码内常量/字面量。三层各自合理，但缺少统一的“哪些可调、默认值在哪、调优边界是什么”的索引。
- 超时/重试/并发/缓冲区存在较多**命名常量**（如 `eventBusConsumerTimeout`、`EventBusDrainTimeout`、`defaultMaxConcurrent`、`cloudFPLookupBatchSize`），这是好信号；但仍有不少关键值散落为字面量，调优需读代码。
- `context.Background()+WithTimeout` 在异步/脱离 HTTP 生命周期任务中广泛存在，部分已在 01/02 审计中定性，07 关注其**超时值治理**：预算公式、封顶值、重试余量应有统一约定与观测。
- 环境变量使用很少（生产代码仅 `BDINFO_WORKERS` 和 `PTF_*` 配置绑定），整体可控；风险主要是“隐式调参入口”缺文档。

## 2. 重点发现

### 2.1 配置三层分裂，缺少统一调参索引（P2）

**证据**：

- 启动配置：`internal/config/config.go` 定义 `Server/Database/Log/Security/Memory/Debug`；`DefaultConfig()` 给出端口、DB、日志、安全默认值；`loader.go` 通过 Viper 读取 YAML + `PTF_*` env，并显式 BindEnv `log.level`、`database.log_level`。
- 运行时设置：`internal/setting/runtime.go` 定义大量 `Key*` 常量与 `DefaultSeeds`（登录锁定、限流、截图、数据清理、图床、PTGen 等）；`RuntimeConfig` 30s TTL 缓存 + `InvalidateAll()` 版本失效。
- 代码内常量/字面量：`internal/pusher/eventbus.go` 有 `eventBusConsumerTimeout=60s`、`EventBusDrainTimeout=10s`；`internal/httpclient/retry_transport.go` 默认 `MaxRetries=3/BaseDelay=500ms/MaxDelay=30s`；`internal/reseed/engine_preload.go` 有 `preloadBatchSize=500`；同时大量 handler/worker 直接写 `10*time.Second`、`5*time.Minute`、`24*time.Hour` 等。

**风险**：

- 运维/开发调参时不知道“该改 YAML、DB setting、还是代码常量”；同类值可能在不同层重复定义。
- 代码常量改动需要发版；DB setting 可热更新但无集中清单；两者边界不清容易形成隐式契约。

**建议**：

- 建立配置分层约定：**启动级**（需重启/影响进程）进 `config`；**运行时可调**（业务策略）进 `setting`；**代码不变量**（协议/安全上限）保留命名常量并文档化。
- 在 `docs/代码质量审计/` 或 `docs/` 增加“调参清单”附录：键名、默认值、来源层、影响范围、生效方式、建议边界。
- 新增可调值时优先复用 `setting.RuntimeConfig`/config，避免再加散落字面量。

### 2.2 超时与取消预算散落，部分值缺业务注释（P1）

**证据**：

- 生产代码中 `WithTimeout/NewTicker/time.After` 约 142 处；`context.WithTimeout(context.Background(), ...)` 约 23 处（抽样）。
- 代表样例：
  - `internal/pusher/eventbus.go`：消费者超时 `60s` 常量化，且有注释说明依据（消费面 DB 写为主、凭观测调值）——良好范例。
  - `internal/api/publish_torrents_handler_execute.go`：站点批量发布预算 `len(req.InfoHashes)*(60s+interval)+30min`，封顶 `24h`；脱离 HTTP 生命周期用 `context.Background()` 派生——有业务理由，但预算公式和封顶值写在 handler 内。
  - `internal/api/orphan_handler.go:168`、`internal/api/update_handler.go:323`、`internal/api/site_handler_crud.go:550` 等使用 `context.Background()+5min/30s` 执行后台任务，超时值分散。
  - `internal/reseed/cloud_fp.go:266,367` 使用 `Background()+5s/10s`；`internal/reseed/engine_match.go:111` defer 清理用 `Background()+5s`——属于 01 篇已识别的 detach 类模式，07 关注值治理。
  - `internal/httpclient/client.go` 默认 `Timeout 30s`、`IdleConnTimeout 45s`、`MaxIdleConnsPerHost 10`；`site/stats_sync.go` 站点同步单站 `50s` 超时。

**风险**：

- 超时过短导致误杀慢任务；过长导致资源占用和停机拖尾。无统一预算说明时，修改一个值可能破坏相邻假设。
- Background 派生超时若无“为什么脱离父 ctx”的注释，后续维护者容易误改为请求 ctx，或反之造成取消链断裂。

**建议**：

- 对后台/脱离请求生命周期的 `Background()+Timeout` 统一要求注释：脱离原因、预算来源、封顶、失败语义（参考 01 篇附录A）。
- 将高频超时抽为命名常量或配置项：至少区分“外部站点请求”“本地 DB/内部任务”“批量后台任务”“停机排空”。
- 为批量任务预算建立公共 helper（输入数量、单项预算、重试余量、封顶），避免各 handler 自写公式。

### 2.3 重试、退避、并发限制有默认值但分布不一（P2）

**证据**：

- HTTP 重试：`internal/httpclient/retry_transport.go` `DefaultRetryConfig` 为 `MaxRetries=3, BaseDelay=500ms, MaxDelay=30s`；`RetryableCheck` 默认网络错误和 5xx 重试，429 不重试并交由 limiter/WAF freeze。
- 域名限流：`internal/httpclient/domain_limiter.go` `defaultMaxConcurrent=2`，默认窗口 `30 req/60s`（`defaultRPS 0.5`）；冻结有指数退避，封顶 `10min`。
- 并发信号量：`reseed/engine_match.go:392` `sem := make(chan struct{}, concurrency)`；`site/stats_sync.go:97/145` 并发 5/10；`publish_torrents_handler_fetch_postprocess.go:228` 并发 6；`publish_torrents_handler_execute.go:595` 并发 2；`orphan/recovery.go:771` 并发 10。
- 队列/缓冲：`pusher/eventbus.go` 默认 256；`audit/logger.go` 1000；`db/write_queue.go` bufSize 参数；`rss/side_load.go` 1000；`reseed/cloud_fp.go` 1000/5000。

**风险**：

- 同为“并发/限流”却散落在多个模块，缺少全局视角；调大一个并发可能放大站点封禁、DB 压力或内存占用。
- 重试策略已较成熟（429 退避、指数 backoff），但部分业务重试（如 publish/bdinfo/artifact）仍有局部魔法值，缺统一观测字段。

**建议**：

- 为并发/队列容量建立“资源预算表”：CPU/网络/DB/外站三类资源各自上限与理由。
- 将通用重试策略封装为可观测结构（attempt、delay、reason、retryable），业务特殊重试显式标注与通用策略差异。
- 对外站相关并发值优先走站点配置/limiter，而不是固定 goroutine 信号量。

### 2.4 魔法数字仍广泛存在，命名常量覆盖不均（P2）

**证据**：

- 生产代码中时间字面量约 355 处；`const` 形态的超时/间隔/限制/批大小等约 15 处（粗扫口径，仅匹配常见命名）。
- 已命名常量示例：`eventBusConsumerTimeout`、`EventBusDrainTimeout`、`defaultMaxConcurrent`、`preloadBatchSize`、`seedRecordsIndexWarnThreshold`、`cloudFPLookupBatchSize`、`MaxBodySize`、`maxDrainSize`。
- 仍为字面量的典型值：`24*time.Hour` 38 处、`10*time.Second` 等短超时大量散落；`365*24*time.Hour` 在 fingerprint/reseed 负缓存/记录处出现；`5*time.Minute` 作为 preflight/cache/任务预算等多场景复用但语义不同。

**风险**：

- 相同数值在不同语义场景复用时，后续修改容易“误伤”不相关逻辑。
- 字面量难以检索意图；评审时只能看到“10s”，看不到“站点详情页请求超时”。

**建议**：

- 优先治理高风险/高频字面量：外部请求超时、重试上限、批大小、队列容量、缓存 TTL、停机排空。
- 命名规则：`<domain><purpose><unit>`，例如 `siteDetailFetchTimeout`、`publishBatchPreflightCacheTTL`；避免泛名 `defaultTimeout`。
- 对确实局部、一次性、无调优意义的值可保留字面量，但需在附近有语义。

### 2.5 配置校验与默认值较基础，可观测性不足（P3）

**证据**：

- `internal/config/config.go` 的 `Validate()` 校验端口、模式、DB driver、MySQL DSN、日志级别；`DefaultConfig()` 提供基础默认值。
- `internal/setting/runtime.go` `GetInt` 对空值返回 0、`strconv.Atoi` 忽略错误；`GetBool` 支持 `true/1/yes/on`。
- `internal/bdinfo/bdrom/bdrom.go` 通过 `BDINFO_WORKERS` 环境变量覆盖 worker 数（生产代码中少见的直接 env 读取）。

**风险**：

- `GetInt` 解析失败静默回 0，可能把配置错误掩盖成“关闭/无限制/异常默认”，具体影响取决于调用方。
- 直接读取 env 的隐式入口缺文档与边界校验说明。

**建议**：

- `setting.RuntimeConfig` 增加带默认值/范围的读取 helper（如 `GetIntDefault(key, def, min, max)`），解析失败打 Warn 并回退默认。
- 对 env 覆盖入口统一登记：变量名、默认值、允许范围、安全影响。
- 启动时输出关键生效配置摘要（脱敏），便于排障确认“实际跑的是什么配置”。

## 4. 验证建议

- **静态盘点**：对 `24*time.Hour`、`5*time.Minute`、`10*time.Second`、`make(chan ..., N)` 等高频字面量做语义分类，确认哪些应命名。
- **配置回归**：修改 setting/config 默认值时，补单测覆盖默认值、边界值、非法值回退。
- **超时观测**：对关键后台任务记录开始/结束/超时/取消原因日志字段，验证预算是否合理。
- **调参演练**：挑选一个高频值（如 eventbus consumer timeout、站点同步超时）走“改配置-观测-回滚”演练，验证清单可用。
