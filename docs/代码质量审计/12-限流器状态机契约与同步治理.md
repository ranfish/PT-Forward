# 12 限流器状态机契约与同步治理

- **状态**：已完成（三刀 v0.0.1654 落地）
- **日期**：2026-11-26
- **基线**：`c1931e1c`（11 全案三刀落地后，`origin/main` 最新）
- **审计范围**：`internal/httpclient/` 限流器状态机的**域键契约**（配置写入 key 与请求 Acquire key 是否同源）与**字段同步纪律**（配置热替换与在途请求的读写是否成对受锁）。核心实锤：`domain_limiter.go` 的 `concurrentCh` 锁外替换（data race + 取消路径永久阻塞）与 `transport.go`/`adapter/factory.go` 的域键口径分裂（站点 `fetch_rps` 配置在主抓取路径失效）；同型核验 `api/site_handler.go` 的第三套 key 口径。
- **审计方法**：全库盘点 626 个生产 Go 文件、避开 01-11 已覆盖维度后据实立项；逐个核对限流器配置写入点与请求取配额点的 key 生成逻辑，核对 `concurrentCh` 字段的所有读写是否成对持锁；用本地离线驱动单测对三处缺陷分别实证（域键失效探针、8 goroutine `-race` 竞态探针、取消路径阻塞探针）；对照 09（明确排除限流算法本身）/10（map 裸写 fatal）划清边界。
- **证据文件**：`evidence/tool-versions.txt`（工具版本+基线）、`evidence/domain-limiter-repro.txt`（三处探针真实输出）。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。所有证据均来自本地离线驱动构造伪 key，未接触靶机或真实用户数据。

## 1. 结论摘要

- 本篇是全库盘点后新立的独立方向，治理对象是**限流器状态机的两个契约**：一是"配置写到哪个桶"与"请求从哪个桶取"必须是同一把 key（域键契约）；二是"字段被热替换"与"在途请求读写该字段"必须成对受锁（同步纪律）。与前序篇正交：09 治理 HTTP 边界资源并明确把"限流/熔断算法本身"排除在篇外；10 的病灶是 `compileRegex` 读侧放锁后裸写 map（runtime fatal），本篇是 channel 字段竞态 + 域键语义不一致，机制与症状均不同；07 只管数值大小，本篇管 key 口径。
- **确认两处真 bug（均离线驱动实证）**：
  - V-01（域键分裂，中危）：主抓取路径的 client 由 `NewHTTPDoerWithSite` 构造、`SiteHTTPConfig.Domain` 留空（`adapter/factory.go:24-33`），`RoundTrip` 用 `extractOrigin` 得到 `https://host` 作为 Acquire key（`transport.go:121-131,166-169`）；而站点 `fetch_rps` 经 `RegisterSiteRateLimit` 写到**去 scheme 的裸 domain**（`factory.go:194-202`）。两者永不相等——站点 RPS 配置在主抓取路径完全失效，实际请求跑默认 0.5 RPS（30 次/分），与配置意图（如 keepfrds 0.0667 RPS=4 次/分）差 7.5 倍。
  - V-02（`concurrentCh` 热替换竞态，高危）：`SetDomainConfig` 在 `:83` 持 `state.mu` 替换 channel 引用，而 `Acquire`/`Release` 在 `:94/:107/:130/:152` 四处**无锁读**该字段。`-race` 离线探针稳定报 DATA RACE（栈顶 `:94` 读 vs `:83` 写）；且 ctx 取消分支从"新空 channel"阻塞接收，探针实证 goroutine 永久卡死、token 永不释放。
- **同型口径（F-01，低危）**：`api/site_handler.go:53-71` `applySiteMaxConcurrent` 写 `"https://"+domain`，仅在 https/无端口时与 `extractOrigin` 巧合一致，与 `RegisterSiteRateLimit` 的裸 domain 口径又冲突——三套 key 并存是 V-01 的结构性根因。
- **正面结论**：`circuit_breaker_transport.go:179-188` 的 `getOrCreate` 正确持锁（同包正例），说明项目内已有正确的状态机同步范式；本篇问题集中在 `domain_limiter.go` 一处。
- **明确不做**：改 RPS/并发数/冻结时长等数值（07 范畴）、改 HTTP 状态码判定（09 候选）、UTF-8 字节截断（影响偏弱）、碰靶机验证。

## 2. 重点发现

### V-01 · 域键口径分裂——站点 RPS 配置在主抓取路径失效（中危 · CVSS 5.3）

- **级别**：中危（CVSS v3.1 `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` = 5.3；阅读档「中危」）——配置静默失效、可致站点超频触发 WAF 封禁，非崩溃。
- **证据**（基线代码四处）：

```go
// 写入：adapter/factory.go:194-202（RegisterSiteRateLimit）
d := strings.TrimPrefix(strings.TrimPrefix(domain, "https://"), "http://")  // 裸 domain
GlobalLimiter.SetDomainConfig(d, DomainLimitConfig{MaxReqs: int(rps*60), WindowSecs: 60, MaxConcurrent: 2})

// 读取：httpclient/transport.go:121-131（RoundTrip）
domain := t.domain
if domain == "" { domain = extractOrigin(req.URL) }   // 主路径 Domain 为空 → https://host
t.limiter.Acquire(req.Context(), domain)

// extractOrigin：transport.go:166-169
func extractOrigin(u *url.URL) string { return u.Scheme + "://" + u.Host }

// 主路径构造：adapter/factory.go:24-33（NewHTTPDoerWithSite）
cfg := httpclient.SiteHTTPConfig{ProxyURL: proxyURL, SkipSSLVerify: skipSSLVerify}  // Domain 不设
```

  `provider.go:218-221` 在 `GetAdapter` 时调 `RegisterSiteRateLimit(site.Domain, site.FetchRPS)` 写裸 domain 桶；主抓取路径的 client（RSS 拉取、详情页抓取等经 `NewHTTPDoerWithSite`）Acquire 走 `https://host` 桶——两者永不相等。默认 `GlobalLimiter = NewDomainRateLimiter(0.5)`，`getOrCreate`（`domain_limiter.go:48-66`）给出默认 30 次/分，配置值从未进入该桶。
- **影响**：站点 `fetch_rps` 特调（如 keepfrds 4 次/分）对主抓取路径无效，实际跑 30 次/分（7.5 倍超速）。注释声称的"fetch_rps 配置生效闭环"（`client.go:134`、`provider.go:219`）并未闭环；超速可触发站方 WAF 冻结/封禁，是 `§59.340` 流控探究要规避的核心风险。
- **复现**（离线探针，同包驱动 `NewDomainRateLimiter(0.5)`）：`SetDomainConfig("example.com", MaxReqs:1)` 后 `Acquire("https://example.com")` 两次——若配置生效第二次应阻塞至 ctx 超时，实测**第二次立即成功**：

```
zz_domainkey_probe_test.go:27: 域键分裂实证：SetDomainConfig(裸 domain) 未影响 Acquire(https://domain)，第二次立即成功——站点 rps 配置失效
--- FAIL: TestZZDomainKeySplitProbe
```

- **整改**：抽取**单一 key 规范化函数**（如 `originKey(string) string`），所有 `SetDomainConfig`/`Acquire`/`Release`/`Freeze` 调用点统一经它生成 key；建议以 `extractOrigin` 的 `scheme://host` 为权威，`RegisterSiteRateLimit` 与 `applySiteMaxConcurrent` 改为写同一 key（注意 http/端口/无 scheme 输入都要归一到同一形态，避免从字符串猜测——最好由目标 URL 推导）。 Add `AssertKeyConsistency` 启动期自检：配置写入 key 与同 domain 请求 key 必须相等，不等则 fail-fast。

### V-02 · `concurrentCh` 锁外替换——data race + 取消路径永久阻塞（高危 · CVSS 7.5）

- **级别**：高危（CVSS v3.1 `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H` = 7.5；阅读档「高危」）——并发状态机数据竞争 + goroutine 永久泄漏。
- **证据**（基线 `domain_limiter.go`）：

```go
// 写（持锁）：:69-86
state.mu.Lock()
if cfg.MaxConcurrent > 0 {
    state.maxConcurrent = cfg.MaxConcurrent
    state.concurrentCh = make(chan struct{}, cfg.MaxConcurrent)   // :83 替换引用
}
state.mu.Unlock()

// 读（无锁）：四处
case state.concurrentCh <- struct{}{}:   // :94  Acquire 入口
    ...
case <-ctx.Done():
    <-state.concurrentCh                  // :107 冻结等待取消——阻塞接收
...
case <-ctx.Done():
    <-state.concurrentCh                  // :130 速率等待取消——阻塞接收
...
select { case <-state.concurrentCh: default: }  // :152 Release
```

  写持 `state.mu`、读不持锁 → data race；且 `:107/:130` 的取消分支对"当时字段指向的 channel"做阻塞接收，而该字段可能已被替换。
- **影响**（三种并发后果）：
  1. **data race**：`-race` 下并发 `Acquire`/`Release` + `SetDomainConfig` 稳定报警，状态机行为未定义。
  2. **goroutine 永久泄漏**：goroutine 在旧 channel 取得 token 后进入冻结/速率等待；`SetDomainConfig` 把字段换成新空 channel；ctx 取消走 `:107/:130` 从**新空 channel** 阻塞接收——永久卡死，且旧 token 永不释放（并发槽永久少一个）。
  3. **并发上限漂移**：旧 token 在 A channel，`Release` 从新 channel B 取（走 default），旧 token 丢失，实际并发可超出上限。
- **复现**（离线探针，见 `evidence/domain-limiter-repro.txt`）：
  - 竞态：8 goroutine 循环 `Acquire/Release` + 1 goroutine 循环 `SetDomainConfig(MaxConcurrent: 2↔4)`，`-race` 实测：

```
WARNING: DATA RACE
  domain_limiter.go:94 +0x304      ← 无锁读
  domain_limiter.go:83 +0x33b      ← 持锁写
```

  - 取消阻塞：`Freeze(key, 3s)` 令 Acquire 进入等待→热替换 channel→`cancel()`，实测 500ms 内 goroutine 未退出：

```
取消路径永久阻塞实证：ctx 取消后 goroutine 仍卡在从新空 channel 接收
--- FAIL: TestZZCancelPathHangProbe
```

- **调用前提**：`SetDomainConfig` 的三个调用点（`client.go:72` 构造时、`provider.go:220` `GetAdapter` 时、`site_handler.go:68` 配置保存时）均可能与正在 `RoundTrip` 的请求并发，非理论时序。
- **整改**：核心原则是**不在热更新时替换 channel 引用**。最小改法：在 `Acquire`/`Release` 入口先持 `state.mu` 取出 channel 的**本地引用** `ch := state.concurrentCh`，解锁后所有发送/接收/取消分支都用同一个 `ch`，确保"取 token 的 channel"与"还 token 的 channel"一致；取消分支用 `select { case <-ch: ...; case <-ctx.Done(): return }` 的非阻塞式归还替代裸阻塞接收。彻底改法：并发槽改为**计数式信号量**（`atomic.Int64` + 条件变量），调整 `maxConcurrent` 只改数值不换引用，从根上消除"跨 channel 错配"。同时热更新前需处理旧 channel 上的在途 token（迁移或排空），否则并发上限仍会漂移。

### F-01 · 第三套 key 口径（低危）

- **级别**：低危（结构性根因登记）。
- **证据**：`api/site_handler.go:53-71` `applySiteMaxConcurrent` 写 `rateKey := "https://" + domain`，仅在 https 且无端口时与 `extractOrigin` 巧合一致；与 `RegisterSiteRateLimit` 的裸 domain 口径冲突。`transport.go:166` 注释已记录曾把 `extractDomain` 改名 `extractOrigin` 以隔离 host/origin 语义，但 key 生产者侧未同步统一。
- **整改**：并入 V-01 的单一 key 规范化函数，消除第三套口径。

### 正面结论：同包正确范式

`circuit_breaker_transport.go:179-188` 的 `getOrCreate` 在 `mu` 内读写 map、外层调用持锁，是同包内正确的状态机同步范式——说明问题集中在 `domain_limiter.go` 一处，治理=补齐该点+统一 key，非重写限流体系。

## 3. 整改建议

- **刀1（V-01+F-01）**：抽取单一 `originKey` 规范化函数，统一所有 `SetDomainConfig`/`Acquire`/`Release`/`Freeze` 调用点的 key 生成；加启动期 key 一致性自检（配置写入 key 与请求 key 必须相等）。
- **刀2（V-02）**：`concurrentCh` 改为"锁内取本地引用、锁外统一使用"，取消分支用非阻塞归还；或彻底改计数式信号量，热更新只改数值不换引用；处理旧 channel 在途 token 迁移。
- **刀3（防回归锚）**：①域键契约锚（Acquire 用配置同 key，断言限流生效，防配置再次静默失效）②限流字段竞态锚（并发 Acquire/Release + SetDomainConfig，`-race` 零 DATA RACE）③取消路径锚（冻结+替换+取消须在超时内退出，防 goroutine 泄漏永久化）。锚须做阴性对照（退回裸 key / 锁外替换 channel → 锚须 FAIL 或 RACE，确认可触发，08 篇方法论）。
