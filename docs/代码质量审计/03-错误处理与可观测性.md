# 03 错误处理与可观测性

- **状态**：已完成（刀A/C/E v0.0.1589+刀B v0.0.1590·刀D 归 04 篇）
- **日期**：2026-11-24
- **基线**：`16f1d052`（`fix §59.563 刀C flush/free_end 残留 ctx 清账（审计 02 §3.2·02 篇整改收官）`）
- **审计范围**：`internal/` 生产代码（排除 `_test.go`、`vendor/`）的错误处理与可观测性；重点关注静默失败、日志上下文、API 错误响应、后台任务生命周期日志。
- **审计方法**：全局扫描 `_ =`、`logger.Error/Warn/Info`、500 响应、zap 字段命名；对高风险忽略错误、日志缺字段、API 错误处理路径做定点读代码。

> 本文为代码质量定点精读结论，不是安全评估结论。行号与统计为基线快照，实施前请重新定位。

## 1. 结论摘要

- 非测试代码共扫描到 **355 处** `_ =`。多数为可接受的低风险忽略（`Close`/`Drain`/已知格式解析/HTTP 写响应），但存在少量**高价值静默失败**，其中发布结果落库被忽略最值得优先修复。
- `logger.Error` 86 处、`logger.Warn` 485 处、`logger.Info` 348 处，整体使用 zap 结构化日志；请求中间件已提供 4xx/5xx 请求级日志，但部分 handler 在返回 500 时未记录业务错误原因，排障仍需补上下文。
- zap 字段命名存在轻度不一致（如 `site`/`site_name`/`target_site`），短期不必大扫除，但新增代码应遵循统一约定。
- API 有 204 处 `http.StatusInternalServerError` 响应；部分响应把内部 `err` 直接拼入 message 返回给客户端，存在内部细节暴露和错误契约不稳定问题。

## 2. 重点发现

### 2.1 发布结果落库静默失败（P1）

**证据**：

- `internal/publish/executor.go:373`：`_ = e.pipe.CreateResult(ctx, &model.PublishResultRecord{...})`
- `internal/publish/executor.go:411`：同类忽略。
- `internal/publish/pipeline.go:538`：`CreateResult` 返回 `error`，实现为 `p.db.WithContext(ctx).Create(result).Error`。

**风险**：

- 发布流程已执行，但历史/审计记录落库失败时无日志、无返回、无补偿。
- 会造成“发布状态/历史缺失”，影响排障、去重记忆、运营统计和后续自动化判断。

**建议**：

- 最低要求：记录 `Warn/Error` 日志，包含 `target_site`、`source_site`、`info_hash`/`pieces_hash`、`status`、`trigger`、`err`。
- 若该记录是发布链的强一致审计依赖，评估返回错误或引入重试；若允许最终一致，也应有可观测告警。

### 2.2 审计/调度副作用错误被忽略（P2）

**证据**：

| 位置 | 现象 | 风险 | 建议 |
|---|---|---|---|
| `internal/site/site_data.go:248` | `_ = db.Create(&model.OperationAuditLog{...}).Error` | 启动对账删除幽灵站点后审计留痕可能丢失 | 至少记录 warn；审计表写入失败不应静默 |
| `internal/reseed/engine.go:185,218` | `_ = e.scheduler.Unregister(...)` | 任务调度注销失败不可见，可能残留旧调度 | 记录 warn，带 `task_id`/`name` |
| `cmd/pt-forward/main.go`、`cmd/pt-forward/rotate.go` | 删除 `encryption_key` 设置忽略错误 | CLI/维护路径，风险较低，但失败原因不可见 | 记录日志或返回错误 |

**说明**：这些点不一定都要改成硬失败，但应避免“完全无痕”。

### 2.3 API 500 响应缺少业务错误日志（P1）

**证据**：

- `internal/api/response.go` 的 `Error/ErrorWithDetail` 只写 JSON 响应，不记录日志。
- `internal/middleware/logging.go` 会在 `status >= 500` 时记录请求级 Error 日志，包含 `method/path/status/duration/remote/request_id`。
- 但部分 handler 直接返回 500，不记录具体 `err`。例如 `internal/api/settings_handler.go:97` 返回“查询设置失败”，未记录 `err`。

**风险**：

- 请求日志能看到“发生了 500”，但不知道根因是 DB、序列化、下游服务还是配置问题。
- 排障时需要复现或加临时日志。

**建议**：

- 约定：handler 在返回 5xx 前记录业务日志，至少包含 `op`、关键标识、`err`；4xx 视噪音情况决定是否 Info/Warn。
- 不要求改造 `response.Error` 自动打日志（容易重复/缺上下文），优先在 handler/service 边界补结构化日志。
- 逐步推广 `request_id` 贯穿后台任务与下游调用日志（中间件已有 request_id）。

### 2.4 内部错误细节直接暴露给客户端（P2）

**证据**：

- 全仓 204 处 `Error(w, http.StatusInternalServerError, ...)`。
- 部分调用把 `err` 拼入 message，如 `internal/api/publish_torrents_handler_torrents.go` 多处 `fmt.Sprintf("连接下载器失败: %v", err)`。

**风险**：

- 内部错误字符串可能包含主机、路径、驱动、下游服务细节，不适合作为稳定 API 契约。
- 客户端可能依赖不稳定错误文本做判断。

**建议**：

- 对外 message 保持稳定、用户可理解；详细 err 只写入服务端日志。
- 需要给前端展示细节时，使用受控的 `detail/code`，避免直接透传原始 `err.Error()`。
- 新增 5xx 响应默认使用固定 message + 服务端日志。

### 2.5 可观测性字段命名不一致（P3）

**证据**（非测试代码粗略统计）：

| 字段 | 次数 | 说明 |
|---|---:|---|
| `zap.String("site", ...)` | 213 | 最常见 |
| `zap.String("site_name", ...)` | 11 | 少量 |
| `zap.String("target_site", ...)` | 4 | 少量 |
| `zap.String("siteName", ...)` | 1 | 风格不一致 |

**风险**：

- 日志检索和仪表盘聚合时需要兼容多个字段名。
- 新代码复制旧字段名会继续扩散。

**建议**：

- 不做全量机械替换；先定约定文档：站点统一 `site`/`target_site`/`source_site` 语义，标识符统一 snake_case 字段名。
- 在触达相关文件时顺手收敛；新增日志遵循约定。

### 2.6 `_ =` 使用需要分级治理（P2）

**证据**：

- 非测试代码 `_ =` 共 355 处。
- 低风险常见形态：`resp.Body.Close()`、`io.Copy(io.Discard, ...)`、HTTP `w.Write`、已知格式 `strconv.Atoi`、测试/兼容性占位。
- 高风险形态：DB Create/Update/审计落库、调度注销、关键副作用。

**建议**：

- 建立分级约定：  
  - **可忽略**：Close/Drain/纯展示写入失败且无后续影响，需在上下文明显或已有注释。  
  - **应日志化**：审计、调度、缓存刷新、非关键落库。  
  - **应返回/重试**：影响业务正确性、数据一致性、状态机推进的写入。
- 评审时重点扫 `Create/Save/Update/Delete/Exec/Reload/Unregister` 等副作用调用。

| P3 | 日志字段命名约定化 | 提升检索/聚合一致性 | 低 | → 刀E v0.0.1589 已完成（附录B） |

## 4. 验证建议

- **代码评审**：新增 `_ =` 必须说明为何可忽略；涉及 DB/调度/审计副作用默认不可忽略。
- **日志抽查**：人为触发几个 5xx 场景，确认请求日志能关联到业务错误日志（request_id/op/err）。
- **回归测试**：对发布历史落库失败场景补测试（可通过 mock pipeline/repo 注入错误），确认不会静默。
- **前端兼容**：若收敛 5xx message，先确认前端是否依赖精确字符串。
