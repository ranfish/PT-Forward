# 08 站点适配器复用治理

- **状态**：精读完成，整改建议待实施
- **日期**：2026-11-26
- **基线**：`9d1e4239`（§59.578 附 Death 案销案）
- **审计范围**：`internal/adapter/` 生产代码（40 个生产文件、约 1.6 万行、12 个 adapter 结构体）及 `internal/model`/`internal/site`/`internal/publish`/`web` 中与框架标识、公共 helper、URL 基址相关的调用面。
- **审计方法**：盘点 adapter 结构体与接口实现、factory 路由与框架默认值表、包内/跨包同名 helper、URL 基址构造、API 请求骨架与既有复用约定（`apihelper.go` 的「共享机制·不共享方言·三次法则」）；对疑似重复逐项读实现核实，区分「真重复」「方言差异」「接口实现同名」三类；对 helper 等价性用 `git log -L` 核对创建以来的变更史；所有结论对照 `docs/31` 设计决策校正。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。

## 1. 结论摘要

- adapter 包的复用底座**已经成型**，不是「一盘散沙」：`errors.go` 提供 `drainBody`/`readBody`/`networkError`/`parseError`，`adapter_nexusphp.go` 的 `setCommonHeaders` 被引用 104 次；`apihelper.go` 成文写明「共享机制·不共享方言·三次法则后再升 util」。12 个结构体中有多个通过嵌入 `*GenericAdapter` 复用通用能力。因此**不建议大拆大合**。
- 12 个 adapter 各自实现的 `SearchTorrents`/`GetTorrentDetail` 等方法名相同，是 `model.SiteAdapter` 接口实现，**不是重复代码**——不纳入整改。
- 最实的问题是**「框架标识」这一概念的表示**：同一概念在七处各抄一份清单，彼此不校验且已经漂移；另有 `nexusphp`/`np` 两套词汇域混用（P2）。
- URL 基址存在三套 helper。`siteBaseURL` 与 `resolveBaseURL` 在 helper 层**三态同行为**；`baseURLOf` 是裸取旧形态，与它们 helper 层**不等价**，只因其两个消费点都经 `BuildNexusDownloadURL` 的幂等补协议/去斜杠兜底，端到端才等价（P3）。
- 代码层面可做且论证成立的收敛明确：`baseURLOf` 委托 `resolveBaseURL`——**等价性来自消费点端到端兜底，而非两函数零行为差异**；API 请求骨架在 detail/sl/stats/apiCall 四类方法间重复，机制部分可下沉。**站点正则、方言字段映射、站方特化一律不动**；三套 URL 基址统一到 `siteBaseURL` 属行为变更，不在本轮。
- 两个历史修复（§59.574 手搓 config 副本漏字段、§59.575 `config.Domain` 两种约定并存）的病灶都落在本篇治理的词汇/约定域范畴，收编进附录G。

## 2. 重点发现

### 2.1 框架标识七处手抄、互不校验且已漂移（P2）

**证据**：

「framework 有哪些合法取值」这件事，在代码、测试与前端里至少七处各自维护：

| 位置 | 形式 | 项数 | 覆盖情况 |

| `internal/adapter/factory.go` `FrameworkDefaults` | map | 10 | 上述 8 项 + cola/yemapt/rousi；hdarea/hxpt/piggo 未注册（见下，属有意设计） |

已观测到的具体漂移与边界：

- `model.FrameworkLabels` / `ValidFramework`（`:288`）不认识 `cola`、`yemapt`、`piggo`、`hdarea`、`hxpt`，但这五个在 `Factory.Create` 里都有真实分支；前端标签则缺 `piggo`、`yemapt`。
- `ValidFramework` 与 `FrameworkLabels` 在全仓**仅被 `model_test.go` 引用**，生产代码零调用；8 个类型常量在生产代码也零引用（生产一律用裸字符串）。这是一座「只跟自己的测试对话」的孤岛。
- `TestFrameworkLabels_Completeness` 用测试内手抄的 8 项清单做完整性断言，因此**检测不到与 factory 真实集合的漂移**；`TestFrameworkDefaults_ContainsAll` 只断言 6 项，同样覆盖不全。
- **反例（不是缺陷）**：查 `docs/31` §59.533 刀2 与联合回归项 C，`FrameworkDefaults` 不注册 hdarea/hxpt 是「API-only 无 RSS 站不进（HashStrategy 等字段全 RSS 消费）」的明确设计；piggo 则由 migration173 在站点行上直接写 `hash_strategy=fake_from_id`/`id_strategy=path_segment` 覆盖。这三处空白不应机械补齐，但代码里没有就地注释说明，容易被误判为遗漏。

**风险**：

- 新增一个 framework 时需要改多处、且没有强制检查，漏改不会让任何测试变红（前端标签漏 piggo/yemapt 已是现成例子）。
- 测试里的「完整性」断言基准是手抄子集，给出虚假的安全感。

**建议**：

- 建立 framework 标识规约（附录G）：明确权威来源与各消费点、新增框架时的更新清单，并**写明 `FrameworkDefaults` 的有意不注册规则**。
- 补全 `FrameworkLabels`/常量至 factory 全集，并把完整性测试的基准改为单一来源（而非测试内手抄）——生产零调用，不改变运行时行为。
- 前端标签缺项属展示层文案，改动需走前端构建流程，单独评估。

### 2.2 同一概念两套词汇域：`nexusphp` 与 `np`（P2）

**证据**：

- `sites.framework`（adapter 路由域）使用 `"nexusphp"`，生产代码 92 处；`Factory.Create` 只认 `"nexusphp"`，没有 `"np"` 分支。
- `PublishFormConfig.Framework`（发布表单生成域）中，`"np"` 出现 74 次（主要在 migration 的表单配置 JSON、`publish/form_config_diff.go:119` 的草稿默认值），同时也有 4 处写成 `"nexusphp"`。
- `internal/publish/executor_stages.go` 同时读两个域：`site.Framework == "tnode"` 与 `cfg.Framework == "piggo"`，但没有 `np`↔`nexusphp` 的归一化函数（全仓搜索无 `case "np"` 或别名映射）。
- 两者在各自域内目前能跑通，但「同一个站、同一个框架概念、两种写法」没有成文边界。

**风险**：跨边界传递 framework 值时，若把表单域的 `"np"` 直接送进 `Factory.Create`，会落入 default 分支得到 `GenericAdapter("np")`，而不是 `NexusPHPAdapter`——表现是站点能力静默降级。当前调用链未发现这样的直传，属于潜在风险而非已发生缺陷。

**建议**：在附录G 中明确两个词汇域的边界与取值表；如未来需要跨边界转换，收敛到一个显式归一化函数，而不是在各处散写字符串比较。

### 2.3 URL 基址三套 helper：两套语义等价、一套裸取旧形态（P3）

**证据**：

| helper | 位置 | 语义（代码实态） | 消费面 |
|---|---|---|---|
| `siteBaseURL` | `errors.go:142` | `BaseURL` 非空 → `TrimRight(BaseURL, "/")`；否则 `Domain` 含 `http://`/`https://` → 去尾斜杠直用；否则裸域补 `https://` | hdarea/hdcity/hxpt/nexusphp_edit/piggo 五处；`docs/31` §59.533 附定义为公共单点（收编 hdcity 既有防御）；§59.575 又将 `HxptAdapter.base()` 的手搓拼接收编至此 |
| `resolveBaseURL` | `adapter_mteam_upload.go:276` | `u = BaseURL`，为空则 `u = Domain`；若 `!HasPrefix(u, "http")` 补 `https://`；`TrimRight(u, "/")` 去尾斜杠 | 12 个文件：gazelle/cola/mteam 族/rousi/tnode/yemapt/mtorrent_core/search 等；§59.460 为可乐三面分离站引入。**补协议与去斜杠自 §59.559（`6f7ebacf`）创建起即在**，`git log -L 276,289:internal/adapter/adapter_mteam_upload.go` 仅一条记录，此后零修改 |
| `baseURLOf` | `adapter_generic.go:676` | `BaseURL` 非空 → 裸取；否则裸取 `Domain`（**不补协议、不去斜杠**） | 仅 generic/nexusphp_upload 两处（`:109`/`:57`），均喂给自带幂等补协议的 `BuildNexusDownloadURL` |

**等价性核对（这是本节的关键，不能凭注释下结论）**：

- `resolveBaseURL` 函数头注释讲「纯 Domain 构造」、正文注释讲可乐三面分离，那是**修复前的问题叙述**；代码本体（`:286-289`）早已带 `HasPrefix("http")` 补协议 + `TrimRight` 去斜杠。函数头的历史叙述容易误导，必须以代码本体与 `git log -L` 为准。
- **helper 层不等价**：裸 Domain 输入（`BaseURL=""`, `Domain="pt.site.com"`）时，`baseURLOf` 返回 `"pt.site.com"`，`resolveBaseURL` 返回 `"https://pt.site.com"`。二者不是「同一逻辑两个名字」。
- **真正的语义等价对是 `siteBaseURL` ↔ `resolveBaseURL`**：标准三态输入（① `BaseURL` 非空且含协议 ② `Domain` 含协议 ③ 裸 `Domain`）下两者输出逐字一致，这才是可互相委托的一对。边界注记：第四态「`BaseURL` 非空但不含协议」两者不同（`siteBaseURL` 直接去斜杠返回、`resolveBaseURL` 补协议），不过正常配置里 `BaseURL` 均带协议，此态不影响结论。
- **端到端等价来自消费点兜底**：`BuildNexusDownloadURL`（`download_url.go:25-33`）在入口 `!HasPrefix(base, "http")` 时补 `https://`，并用 `TrimRight(base, "/")` 拼路径——补协议与去斜杠都是**幂等**的。`baseURLOf` 只有两个消费点且都经它，故委托后最终 URL 一致（四态推演见 §3 刀2）。

**风险**：

- `baseURLOf` 的等价性依赖「下游 `BuildNexusDownloadURL` 幂等兜底」这一外部前提，而非自身语义正确；一旦出现第三个不经 `BuildNexusDownloadURL` 的消费点，或 `BuildNexusDownloadURL` 去掉兜底，立即产生行为差异。
- `resolveBaseURL` 的函数头注释与实际代码脱节，后续维护者易据注释误判其语义（本次精读初稿即被误导）。

**建议**：

- 消费点端到端等价的刀次内：让 `baseURLOf` 委托 `resolveBaseURL`；论证口径写「消费点端到端等价（`BuildNexusDownloadURL` 幂等兜底）」，**不写「两函数零行为差异」**。
- 顺手修正 `resolveBaseURL` 函数头注释，使其反映「补协议 + 去斜杠」的代码实态（注释修正零行为变更）。
- **不把 `resolveBaseURL`/`baseURLOf` 的消费面改成 `siteBaseURL`**——虽标准三态语义等价，但消费面广、第四态有差异，属行为变更，需单独评估。

### 2.4 API 请求骨架多处重复，可下沉到既有机制层（P3）

**证据**（按同签名分组，逐处核对）：

- `detailViaAPI` ×3（同签名 `(ctx, config, torrentID) (*model.TorrentDetail, error)`）：`adapter_gazelle.go:164`、`adapter_mteam_detail.go:14`、`adapter_unit3d.go:212`。
- `slViaAPI` ×3（同签名 `(ctx, config, torrentID) (*model.SLData, error)`）：`adapter_gazelle.go:552`、`adapter_mteam_slhr.go:499`、`adapter_unit3d.go:524`。
- `fetchUserStatsAPI` ×4（同签名 `(ctx, config) (*model.UserStatsResult, error)`）：`adapter_gazelle.go:892`、`adapter_mteam_upload.go:312`、`adapter_nexusphp_userstats.go:64`、`adapter_unit3d.go:817`。
- `apiCall` ×2 同签名（`(ctx, config, method, url string, body io.Reader, out any) error`）：`adapter_hdarea.go:127`、`adapter_hxpt.go:128`（§59.570/§59.541 新增）；另有 `adapter_piggo.go:129` 变体（`(ctx, config, path string, body any, out any) (int, []byte, error)`，返回状态码+原始字节，不属同签名组）。
- 这些方法的 HTTP 骨架一致：`http.NewRequestWithContext` → 设头 → `a.doer.Client.Do` → `defer drainBody(resp)` → `readBody`/`io.ReadAll(LimitReader)` → JSON 解析；差异全在方法/URL/请求头/响应结构（方言）。以 `apiCall` 两处为例，鉴权头不同（`X-API-Key` vs `Authorization: Token`）、限流处理不同（好学 429 特判），这些是方言，不得合并。
- 机制层已有 `errors.go` 的 `drainBody`/`readBody`/`networkError`/`parseError`（引用 129/102/159/58 次）与 `setCommonHeaders`（104 次），骨架部分下沉有现成落点。

**风险**：重复的骨架本身不致错，但错误包装口径已有细微差异（有的用 `networkError`/`parseError`，有的直接返回原始 err），后续统一错误处理时容易漏改。

**建议**：**不强行合并整个方法**，只考虑把 `Do → drainBody → readBody → Unmarshal → parseError` 这段纯机制抽成一个 helper，请求构造与响应结构保留在方言层——完全符合 `apihelper.go` 的既有铁律。落地前需逐点核对错误包装等价性；若核对成本高于收益，则只在附录G 里记为规约，不动代码。

### 2.5 跨包同语义小 helper（P3，渐进）

**证据**：

- `adapter_yemapt.go:564` `extractDoubanID` 与 `publish/executor_helpers.go:107` `extractDoubanID` 同名，实现不同（前者委托 `extractNumericID`，后者正则 + 纯数字兜底），语义相近但不确定等价。
- `publish/gpw_inject.go:251` 的 `gpwFirst` 注释明确写着「adapter 层 `firstNonEmpty` 同语义」，属于已知但未提取的重复。
- adapter 包内有 153 个包内私有小函数，分布在 29 个文件——数量本身不是问题，但说明「小工具散落」是常态。

**风险**：低。当前未发现因这些 helper 产生的不一致。

**建议**：遵守既有「三次法则」——出现包外消费者或第三站证明流程稳定时再升公共 util；现阶段仅在附录G 记录现状，不机械搬迁。

### 2.6 历史病灶收编：config 构造的两种约定域（P2，附录G 范畴）

**证据**：两个已修复病灶的根因都落在「同一概念多形态约定、无单点规约」：

- **§59.574（`v0.0.1621`）手搓 config 副本漏字段**：`internal/site/stats_sync.go:202` 的统计同步链自己 `&model.SiteConfig{...}` 构造配置，起初漏带 `DownloadMode`/`DownloadURLTemplate`，导致 `cuhashEnabled` 恒 false、`scrapeCuhash` 永不执行。现已在 `:214-215` 补上，但「手搓副本 vs 走 provider」的分叉仍在。
- **§59.575（`v0.0.1622`）`config.Domain` 两种约定并存**：`internal/site/provider.go:460`/`:477` 取 `Domain: s.Domain`（裸域），而 `stats_sync.go:204` 取 `Domain: site.BaseURL`（带协议完整 URL）。同一 `SiteConfig.Domain` 字段，两条构造链塞入两种形态；§59.575 正是因此炸出 `https://https//...` 双 scheme，最后靠 `siteBaseURL` 三态兼容兜住。

**风险**：兜底已就位，但「`Domain` 到底是裸域还是完整 URL」没有成文约定，后续新构造链仍可能踩同一种坑；这与 §2.2 的 `np`/`nexusphp` 双词汇域同属「约定域治理」。

**建议**：纳入附录G，写明 `SiteConfig.Domain` 的两种现存形态与各自的消费链、构造 config 时优先走 `provider.go` 单点、手搓副本必须逐字段对齐的清单。已修复的两处不再改代码。

### 2.7 正面结论：不应被误判为问题的部分

- **接口实现同名不算重复**：12 个 adapter 的 `SearchTorrents`/`GetTorrentDetail`/`Framework` 等方法同名，是 `model.SiteAdapter` 接口的实现，属于必要结构。
- **机制层已成型**：`setCommonHeaders` 104 处、`drainBody` 129 处、`readBody` 102 处引用，说明公共 HTTP 机制早有收敛，不必重建。
- **嵌入复用已在用**：`ColaAdapter`/`Unit3DAdapter` 等嵌入 `*GenericAdapter`，是合理的复用形态。
- **`adapter/apihelper.go` 已有成文边界**：「共享机制·不共享方言」「包内私有·三次法则后再升 util」。本次治理沿用该约定，不另立标准。
- **`resolveBaseURL` 已带补协议/去斜杠**：不可因其函数头注释的「纯 Domain」历史叙述就判为「裸取」（§2.3 有 `git log -L` 实证）。
