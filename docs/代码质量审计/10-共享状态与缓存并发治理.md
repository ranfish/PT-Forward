## 1. 结论摘要

- 本篇承接 09 篇 §6 点名的最强候选。治理对象是**运行时共享状态的读写纪律**——缓存的读路径与写路径是否成对受锁、懒初始化是否幂等、已有并发单点是否被绕过。与前序篇正交：02 管后台任务的停机编排（`Stop` 链/EventBus）、06 管 race 测试基建与回归锚，本篇只管"运行时数据结构的并发访问正确性"。
- **确认一处可复现真崩溃（P1）**：`internal/filter/engine.go` 的 `compileRegex` 在读侧 `RLock` 释放后，于 `:43` 裸写全局 `regexCache` map（淘汰循环 `:38-42` 与写入 `:43` 全程无锁）。基线离线驱动压测（8 goroutine）实测 `fatal error: concurrent map read and map write`（栈顶 `engine.go:22`）与 `fatal error: concurrent map writes`（栈顶 `engine.go:43`）——Go 的 map 并发写故障**不可 recover、直接终止进程**，且此时 `regexCacheMu` 形同虚设。
- **漏网定性明确**：同类正则缓存 `rss/fetcher.go:369-396`、`rss/engine.go:29-54` 与 §59.186 已修的 `titleparser/dict_loader.go` 均为正确实现（double-check + 写锁 / `sync.Map`），唯独 `filter` 这处漏改——属于 §59.186 修法未扫干净的残留，不是设计上允许的无锁。
- **正面结论**：全库已有 32 处正确使用 `sync.Map`/`atomic.Pointer`/`sync.Once` 的单点（如 `titleparser` 的 `tokenReC2`/`inferReCache`、`rss` 的 `clientCache`/`detectCache`）。问题不在"没有并发原语"，而在**一处绕过点的漏网**。治理=补齐该点并加防回归锚，非重写全部缓存。
- **明确不做**：不停机编排（02 范畴）、不加 race CI 层（06 范畴）、不改缓存容量数值与正则业务语义、不碰站点过滤规则内容本身。

## 2. 重点发现

### 2.1 `filter/engine.go` 的 `compileRegex` 读侧放锁后裸写 map（P1，可复现真崩溃）

**代码事实**（基线 `engine.go:14-44`）：

```go
var (
	regexCache   = make(map[string]*regexp.Regexp)
	regexCacheMu sync.RWMutex
)

func compileRegex(pattern string) (*regexp.Regexp, error) {
	regexCacheMu.RLock()
	re, ok := regexCache[pattern]   // :22 读
	regexCacheMu.RUnlock()          // :23 放读锁
	if ok {
		return re, nil
	}
	// ... 编译 ...
	if len(regexCache) >= 5000 {    // :38 读——锁外
		for k := range regexCache {  // :39 range——锁外
			delete(regexCache, k)    // :40 写——锁外
			break
		}
	}
	regexCache[pattern] = re        // :43 写——锁外
	return re, nil
}
```

三处越界：`len(regexCache)`、range + `delete`、`regexCache[pattern] = re` 全在 `RUnlock()` 之后、且从未加写锁。当两个 goroutine 同时 miss 同一批 pattern（或缓存满触发淘汰）时，并发写直接触发 runtime fatal。

**证据**（离线驱动压测，8 goroutine × 2000 次，本地临时探针跑完即删）：

```
fatal error: concurrent map writes

goroutine 11 [running]:
internal/runtime/maps.fatal(...)
github.com/ranfish/pt-forward/internal/filter.compileRegex(...)
	/home/incast/work/engagements/10.0.0.49/PT-Forward/internal/filter/engine.go:43 +0x24c
```

第二次运行复现读/写交叉：

```
fatal error: concurrent map read and map write
	.../internal/filter/engine.go:22 +0x85
	.../internal/filter/engine.go:43 +0x24c
	.../internal/filter/engine.go:33 +0x1a5
```

栈顶 `:22`（读）与 `:43`（写）与基线描述完全吻合。原始输出见 `evidence/filter-fatal-repro.txt`。

**调用前提**：`compileRegex` 由 `MatchConditionExport` 在 `CompareRegExp`/`CompareNotRegExp` 分支调用（`engine.go:142,148`），经 `Engine.Match`/`MatchByIDs` 进入。过滤引擎在种子入库路径被并发调用（见 `engine_bench_test.go` 并发基准），叠加 RSS 拉取/辅种/发布多 goroutine 路径，真实并发触达是可达的——不是纯理论竞态。

**影响**：进程级崩溃（不可 recover），会导致种子过滤/入库链路整体中断；在高频正则规则场景（多规则、多样式 pattern）下命中概率随并发度上升。

**整改**：参照 `rss/engine.go` / §59.186 的既有修法——读侧 miss 后改拿写锁并做 double-check（`if _, exists := regexCache[pattern]; exists { ... }`），淘汰与写入全部移入写锁临界区。或直接用 `sync.Map`（`Load`/`LoadOrStore`），与 `titleparser` 单点一致。**不建议**用全程 `Lock` 替代 `RLock`（会牺牲热路径读性能，且不符合已确立的 double-check 惯例）。

### 2.2 同类缓存对照——漏网而非普适缺陷（正面结论）

逐一核对全库 package 级正则/懒缓存的读写纪律：

| 位置 | 形态 | 判定 |
|---|---|---|
| `filter/engine.go:20-44` | `RWMutex` 读侧放锁后裸写 map | **缺陷**（2.1） |
| `rss/fetcher.go:369-396` | `RLock` miss → `Lock` → double-check → 写 → `Unlock` | 正确 |
| `rss/engine.go:29-54` | `RLock` miss → `defer Lock/Unlock` → double-check → 写 | 正确 |
| `titleparser/dict_loader.go:120-124,436-437` | `sync.Map`（`tokenReC2`/`inferReCache`）§59.186 已修 | 正确 |
| `httpclient/chrome_transport.go:36-42` | `sync.Mutex` 全临界区 | 正确 |

结论：`regexCacheMu` 在 `filter` 是唯一"声明了锁却没锁住写"的点。§59.186 修了 `titleparser` 却漏了 `filter`，本篇补上即可闭合同类问题。

## 3. 整改建议

- **刀1（P1）**：`filter/engine.go` 的 `compileRegex` 补齐写侧同步——采纳 `rss/engine.go` 的 double-check + 写锁范式（读热路径仍走 `RLock`，miss 才升级写锁），把 `:38-43` 的淘汰与写入移入写锁临界区。
- **刀2（防回归锚）**：新增 `internal/filter` 并发压测锚——离线驱动 N goroutine 并发调用不同 pattern 的 `compileRegex`，断言无 fatal、缓存最终条目数正确；纳入 06 篇既有 race CI 层的覆盖包清单（只加测试，不改 CI 基建）。
