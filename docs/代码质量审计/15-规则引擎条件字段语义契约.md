## 1. 结论摘要

- 本篇是全库盘点后新立的独立方向。盘点在 01-14 之外找到两个正交且证据扎实的确凿功能性缺陷；本篇聚焦**规则引擎条件字段语义契约**——有文档白纸黑字的契约、有业务核心需求背书、有本地离线实锤，且复现与时区/上游形态无关。
- **确认两处确凿功能性缺陷（V-01/V-02，中危）**：同一条件键 `downloadUploadRatio` 在两条求值路径上双重损坏。
  - **V-01（声明式语义反转）**：文档 `docs31:7757` 规定「上传=0 时为 +∞」、`:7674` 明确黑车检测是核心需求，但 `rule/evaluator.go:137-141` 与 `seeding/rule_evaluator.go:133-139` 在 `UploadSpeed==0` 时均返回 `"0"`——黑车最典型的"只下不传"形态下，`downloadUploadRatio > 阈值` 恰好不命中，业务语义完全颠倒；两处还额外加了文档未声明的 `TotalSize > 0` 门槛。
  - **V-02（expr 路径字段缺失）**：两个 expr 环境及构建函数均无该字段，`expr.Compile("downloadUploadRatio > 5", ...)` 实测 `unknown name`，expr 规则静默失效；文档 `docs31:46722` 声称「42/42 全覆盖」不成立。
- **次要候选（F-01，低危·需取证）**：双实现 `!known` 分支对未知操作符 `default: return true`（放行），拼错操作符会让条件恒真、规则静默生效；两处枚举分组写法不同但语义等价，主要问题是"放行"这一默认行为本身。当前未取到真实规则数据中的未知字段/操作符形态，属契约治理、需取证。
- **正面结论**：盘点独立核验零除数守卫（`scoring.go:60-71` 对 `Seeders==0` 显式分 0/99999，与本篇缺陷形成"作者已意识到同类问题、此处是遗漏"的强力佐证）、本地时间口径正例、迁移版本纪律、并发原语等均健康，不作主导。
- **登记但未纳入本篇**：候选「`Truncate(24h)` 日界偏移」（9 处使用点，UTC+8 下"今日"起点落在 08:00）已离线复现确凿，但属时间分桶口径、与本篇主题不同，且显现依赖部署时区形态——登记为第 16 篇候选，见 §5。

## 2. 重点发现

### V-01 · `downloadUploadRatio` 零上传语义反转（中危 · 声明式求值路径）

- **级别**：中危（阅读档「中危」；技术档参照 `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:L`）。核心业务规则在最该触发的场景失效；无数据损坏、无越权。
- **证据**：

```go
// docs/31-模块设计决策记录.md:7757（契约定义）
| 20 | `downloadUploadRatio` | float64 | 下载/上传速度比（downloadSpeed/uploadSpeed，上传=0 时为 +∞） |
// docs/31:7674（业务背景）
| 黑车检测（下载速度远大于上传）是核心需求 | 条件键新增 `downloadUploadRatio`，预置 8 档分级表模板 |

// internal/rule/evaluator.go:137-141
case "downloadUploadRatio":
    if c.TotalSize > 0 && c.UploadSpeed > 0 {
        return fmt.Sprintf("%.4f", float64(c.DownloadSpeed)/float64(c.UploadSpeed)), true
    }
    return "0", true

// internal/seeding/rule_evaluator.go:135-139
if ti.TotalSize > 0 && key == "downloadUploadRatio" {
    if ti.UploadSpeed > 0 {
        return fmt.Sprintf("%.4f", float64(ti.DownloadSpeed)/float64(ti.UploadSpeed)), true
    }
    return "0", true
}
```

  文档契约 `+∞` 与实现 `0` 方向相反。`TotalSize > 0` 门槛未在任何契约中出现——零大小种子（如刚建任务尚未拿到元数据）即便有上传速度也被归零。
- **影响**：零上传正是黑车典型形态（`UploadSpeed==0` 且 `DownloadSpeed` 很大）。契约要求此时返回 `+∞` 以触发 `downloadUploadRatio > 阈值` 的删种/保护规则；实现返回 `0` 使该规则恰好不命中——黑车检测在最该工作的场景失效。反之，若规则用 `smaller` 做低比例保护，`0` 又会误命中。前端 `web/src/views/seeding/SeedingRuleList.vue:381/601` 确实暴露该字段供用户配置，影响面可达真实规则。
- **复现**（本地真实 `Context.fieldValue`，见证据文件）：

```
零上传（黑车典型）: value="0" ok=true  ← 文档契约要求 +∞
有上传对照: value="5.0000"
```

- **对照佐证**：同库 `internal/seeding/scoring.go:60-71` 对 `Seeders==0` 显式分 `0`/`99999`（零除数不返回误导性的 0 或除零），说明作者已意识到同类语义、此处是遗漏而非有意设计。
- **整改**：零上传时返回 `+∞` 语义（如 `math.Inf(1)` 格式化或明确的最大哨兵值，需与 `compareNumeric` 的数值解析兼容），并去掉文档未声明的 `TotalSize > 0` 门槛；新增零上传契约锚（`fieldValue` 结果在 `> 阈值` 比较下须为真）。

### V-02 · expr 路径字段缺失导致规则静默失效（中危 · expr 求值路径）

- **级别**：中危（同上）。expr 规则是该字段的主要使用形态（docs31:7671 记录实战中 20/24 条用 expr），字段缺失使这类规则整体失效。
- **证据**：

```go
// internal/rule/evaluator.go:338-377 ExprEnv 与 internal/seeding/context.go:12-56 exprEnv
// 两者字段列表均无 downloadUploadRatio；各自 buildExprEnv（:378 / :58）亦未填充。
// 而文档 docs31:46722 声明「下载器实时 (17) ... downloadUploadRatio」42/42 全覆盖。
```

  本地真实 `expr.Compile` 复现：

```
expr 编译 downloadUploadRatio: err=unknown name downloadUploadRatio (1:1)
expr 编译已有字段 ratio 对照: err=<nil>
seeding expr 编译 downloadUploadRatio: err=unknown name downloadUploadRatio (1:1)
```

- **影响**：用户按前端可选字段配置 `downloadUploadRatio > 5` 的 expr 规则，在编译期即因未知标识符失败。`getOrCompileProgram`（`rule/evaluator.go:440-445`）的编译错误若被上层静默处理，规则表现为"配了但不生效"，黑车保护形同虚设。文档"42/42 全覆盖"声明失实。
- **整改**：两个 `ExprEnv`/`exprEnv` 补 `DownloadUploadRatio float64 \`expr:"downloadUploadRatio"\`` 字段，并在各自 `buildExprEnv` 按 V-01 的同一语义填充（保证声明式与 expr 两条路径口径一致）；新增 expr 编译锚（`downloadUploadRatio > 5` 须编译成功）与 42/42 覆盖锚（文档所列键逐项在两环境中存在）。

### F-01 · 未知字段/操作符默认放行（低危 · 契约治理，需取证）

- **证据**（`internal/rule/evaluator.go:241-259`、`internal/seeding/rule_evaluator.go:514-528`）：

```go
fv, known := c.fieldValue(cond.Field)
if !known {
    switch cond.Operator {
    case "bigger", ">", "smaller", "<", ...:
        return false
    default:
        return true   // 未知操作符（含拼写错误）一律放行
    }
}
```

  两处写法不同（一处显式列出字符串类操作符、一处走 default），但语义等价：未知字段时数值比较类返回 `false`，其余（含未知操作符）返回 `true`。
- **影响**：条件键或操作符拼写错误（如 `biggerThen`）会落入 `default: return true`，使条件恒真、规则静默生效——若该条件位于删种规则中，可能造成误删。这是"静默放行"这一默认行为本身的契约问题，非两实现分歧。
- **取证缺口**：未取到真实规则数据中是否存在未知字段/操作符形态，无法证明当前已发生功能损坏——标注「未验证/推断」。
- **整改**：评估将 `!known` 默认改为「拒绝并记录告警」的兼容性影响；若需保留容错，至少对未知操作符显式报错或落日志，让拼写错误显性化。实施前须取证真实规则数据。

### 正面结论：经核验健康的维度

- 零除数处理：`scoring.go:60-71` 对 `Seeders==0` 显式分支；`rule/evaluator.go:172,415`、`seeding/rule_evaluator.go:178`、`seeding/context.go:75` 磁盘占用率均有 `TotalSpace>0` 守卫。
- 本地时间口径正例：`scoring.go:184 TimeWindow.Contains`、`discount_checker.go:38 IsWithinActiveWindow` 用本地小时，与调度器 `cron.WithLocation(time.Local)` 一致；`reseed/engine_preload.go:41` 每日限额用本地日期。
- 迁移纪律：`internal/db` 183 个 `RegisterMigration` 版本无重复号、`RunMigrations` 按版本排序。
- 并发原语：OTA 单飞门 `atomic.Bool` + `CompareAndSwap` 正确。
- 历史沿用：atomic 类型化 API、`sync.Once` embed 懒加载、类型断言守卫、`%w` 错误链、SQL 非 LIKE 拼接白名单、分页边界、`strings.Index -1` 守卫、TTL 边界、retry_transport、`maskToken` 长度守卫。

## 3. 整改建议

- **刀1（V-01）**：零上传返回 `+∞` 语义（与 `compareNumeric` 兼容），去 `TotalSize > 0` 门槛；新增零上传契约锚（`> 阈值` 比较须真、有上传对照值不回归）。
- **刀2（V-02）**：两个 expr 环境补字段并在 `buildExprEnv` 填充；新增 expr 编译锚 + 42/42 覆盖锚，确保双路径口径一致。
- **刀3（F-01 + 三层锚）**：未知字段/操作符默认行为显式化（拒绝或告警，评估兼容性后定）；静态锚登记"条件键文档与双路径实现一致"纪律（登记须附契约来源与双路径核验，沿用 13/14 补刀教训）。新增锚阴性对照：零上传恢复 `0` → 契约锚 FAIL、删 expr 字段 → 编译锚 FAIL、恢复 `default: return true` → 默认行为锚 FAIL。
