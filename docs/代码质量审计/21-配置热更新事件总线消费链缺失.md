## 1. 结论摘要

- 本篇是第 21 篇，由三路盘点据实立项（非预设）。新增方向「配置事件总线零订阅」经精读纠正为「消费链名存实亡」：`ConfigEventBus` 本身实现完整且有生产订阅者，但订阅者只处理图床代理两个键，设计权威明确要求的 RSS 调度器重建 / Seeding 策略重载 / `ReloadSubscription` 全部没有实现。
- **V-01（低—中危·设计一致性/功能缺失）**：设计权威 `docs/31:1770` R-P2-5 明定「ConfigEventBus 订阅站点配置变更 → RSSEngine.ReloadSubscription(subID)」，§16.2 的 6 步流程明定「各模块 subscriber 收到事件 → 重新加载相关配置 / RSS Engine 收到 → 重建调度器 / SeedingEngine 收到 → 重新加载策略」，并以 ✅ 声明 `scheduler.*`、`cookiecloud.*`、`site_monitor.*`、`data_cleanup.*`、`stats.*`、`iyuu.*`、`notification.*` 等键支持热更新。生产侧：`ReloadSubscription` 符号在 `internal/` 全库 0 处（离线复现 ④=0）、`rssEngine.configBus` 字段只声明+赋值从不读取（③=2）、唯一订阅者只处理 `image_host_use_proxy`/`httpProxy` 两键（②=[image_host_use_proxy httpProxy]）。
- **V-02（低危·契约不一致·潜在断链）**：设计权威 `docs/31:11164` 明定 `ChangedKeys` 使用 YAML 点分路径（如 `log.level`、`notification.digest_interval`），而 `settings_handler.go:191/222` 两处 Publish 发的都是 DB setting key（`[]string{key}`，⑤=2/2）。若将来按权威实现按点分路径分发的订阅者，现有发布方发出的 setting key **永远匹配不上**——这是埋着的断链，不是当前已损坏的功能。
- **诚实边界（F-01）**：大部分配置的热更新效果其实由**替代机制**达成——`setting.InvalidateAll()` 使 `RuntimeConfig` 缓存失效（覆盖经 `rc.Get*` 动态读的键），`cookiecloud`/`iyuu` 等每次调用 `getConfig(ctx)` 直接查 DB。因此**不宣称「用户改配置不生效」的生产事故**；可主张的确定事实是「设计权威声明的消费链没有实现，功能效果靠隐式约定兜底，且 ChangedKeys 契约埋着断链」。这一点已由离线复现 ① 佐证：总线本身 Publish→Subscribe 正常。
- **明确不做**：不改生产代码、不碰靶机、不改业务语义；本篇只做精读与整改建议，修复另案。

## 2. 重点发现

### V-01 · 设计权威声明的热更新消费链从未落地（低—中危 · 设计一致性/功能缺失）

- **级别**：技术档无对应 CVSS（非安全边界漏洞，不涉及越权/泄露/DoS）；阅读档 **低—中危**。理由：这是确凿的设计—实现脱节，但当前功能效果由替代机制兜底（见 F-01），用户可感知损伤未取证；若后续按设计扩展依赖事件总线，则升级为中危。

### V-02 · `ChangedKeys` 契约不一致：发布 DB setting key，权威要求 YAML 点分路径（低危 · 潜在断链）

- **级别**：阅读档 **低危**。当前无功能损坏（唯一订阅者只精确匹配两个图床键，恰好是 setting key 形态），但契约错配使「按设计实现通用分发器」的后续工作必然踩空。
- **证据**：`docs/31:11164` 原文「`ChangedKeys` 使用 YAML 点分路径（如 `log.level`、`notification.digest_interval`），与 config.yaml 层级一一对应」；`settings_handler.go:191/222` 两处均为 `ChangedKeys: []string{key}`（⑤=2/2）。离线复现 ① 用权威规定的点分路径 `cookiecloud.url` 发布，总线如实送达——证明总线对键形态无感，错配发生在发布方与权威定义之间。
- **影响**：若按 R-P2-5 补订阅者并按 `log.level`/`cookiecloud.url` 等点分路径分发，来自设置 API 的事件（发的是 `log_level`/`cookieCloudUrl` 这类 setting key）将全部 miss，热更新依旧不生效——即「修了订阅端却仍不工作」的隐蔽返工。
- **整改**：尽早裁决键空间——要么发布方补全「setting key → YAML 点分路径」映射，要么修订设计权威承认 setting key 命名空间；二者必须择一，不可长期两存。

### F-01 · 替代机制兜底，当前不宣称功能事故（诚实边界）

- `setting.InvalidateAll()`（`internal/setting/runtime.go:132`）使全局 config version +1，`RuntimeConfig.get` 据此失效 30s TTL 缓存（`runtime.go:158-175`）——所有经 `rc.Get*`/`GetIntDefault` 动态读的键（限流、登录、下载、发布、调度等包）在事件到达后自动生效。
- `cookiecloud`（`sync.go:315` `getConfig`）、`iyuu`（`service.go:61` `getConfig`）等模块每次调用直接查 DB，配置变更天然在下次调用生效，不依赖事件总线。
- RSS 订阅的 ticker 每轮 `repo.GetByID(freshSub)` 取最新订阅（`rss/engine.go:637-657`），订阅字段变更同样不依赖事件。
- **因此**：设计权威表格里标 ✅ 的多数键，实际效果由「缓存失效」或「每次读 DB」等价达成；本报告的确定结论止于「消费链未实现 + 契约错配」，不外推为「用户改配置不生效」。「哪些键确实因缺少消费链而不生效」——**未验证/推断**，需按具体键逐个取证。

- 与 **18（channel 关闭责任与同步配对）**：18 管 goroutine/channel 生命周期与并发配对；本篇管配置变更事件的发布—订阅接线完整性，无重叠。
- 与 **19（缓存键站点维度）**：19 管单个缓存的键构造；本篇管跨模块事件总线契约。
- 与 **20（运行时字段持久化）**：20 管内存态→DB 字段的持久化保真；本篇管配置变更→运行时的通知链。二者同属「状态传递」家族但方向相反（20 是启动时恢复，21 是运行时变更通知），独立立项。
- 与 **07（配置与魔法值治理）** / **12（限流器状态机）**：07 管配置取值与命名，12 管限流器内部状态；本篇管配置变更的通知接线，正交。

- **刀 1（消费链落地或明示废弃，二选一）**：若按设计权威推进——把 `main.go` 的匿名订阅 goroutine 提取为可测试的公共消费者（如 `rss.StartConfigReloadLoop`），按裁决后的键空间分发到 RSS 调度器重建、Seeding 策略重载等目标；同时让 `rssEngine` 真正使用 `configBus`（消除死字段），实现 `ReloadSubscription(subID)`。若认为设计权威已过时——同时删掉 `SetConfigEventBus`/`configBus` 字段与两处 Publish，并把 docs/31 R-P2-5 与 §16.2 流程改为实态（明确这些热更新靠缓存失效/每次读 DB），避免「文档声明与代码永远对不上」。
