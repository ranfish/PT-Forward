# 08 站点适配器复用治理

- **状态**：精读完成，整改建议待实施
- **日期**：2026-11-26
- **基线**：`9d1e4239`（§59.578 附 Death 案销案）
- **审计范围**：`internal/adapter/` 生产代码（40 个生产文件、约 1.6 万行、12 个 adapter 结构体）及 `internal/model`/`internal/site`/`internal/publish`/`web` 中与框架标识、公共 helper、URL 基址相关的调用面。
- **审计方法**：盘点 adapter 结构体与接口实现、factory 路由与框架默认值表、包内/跨包同名 helper、URL 基址构造、API 请求骨架与既有复用约定（`apihelper.go` 的「共享机制·不共享方言·三次法则」）；对疑似重复逐项读实现核实，区分「真重复」「方言差异」「接口实现同名」三类；所有结论对照 `docs/31` 设计决策校正。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。

## 1. 结论摘要

- adapter 包的复用底座**已经成型**，不是「一盘散沙」：`errors.go` 提供 `drainBody`/`readBody`/`networkError`/`parseError`，`adapter_nexusphp.go` 的 `setCommonHeaders` 被引用 104 次；`apihelper.go` 成文写明「共享机制·不共享方言·三次法则后再升 util」。12 个结构体中有多个通过嵌入 `*GenericAdapter` 复用通用能力。因此**不建议大拆大合**。
- 12 个 adapter 各自实现的 `SearchTorrents`/`GetTorrentDetail` 等方法名相同，是 `model.SiteAdapter` 接口实现，**不是重复代码**——不纳入整改。
- 最实的问题是**「框架标识」这一概念的表示**：同一概念在七处各抄一份清单，彼此不校验且已经漂移；另有 `nexusphp`/`np` 两套词汇域混用（P2）。
- URL 基址存在三套 helper。`docs/31` §59.533 附已把 `siteBaseURL` 定为公共单点，§59.575 又将 `HxptAdapter.base()` 收编到它；但 `baseURLOf` 与 `resolveBaseURL` 仍是同一逻辑两个名字（P3）。
- 代码层面能做的零行为变更收敛有限但明确：`baseURLOf` 委托 `resolveBaseURL`；API 请求骨架在三到四个站点间重复，机制部分可下沉。**站点正则、方言字段映射、站方特化一律不动**；三套 URL 基址统一到 `siteBaseURL` 属行为变更，不在本轮。

## 2. 重点发现

### 2.1 框架标识七处手抄、互不校验且已漂移（P2）

**证据**：

「framework 有哪些合法取值」这件事，在代码、测试与前端里至少七处各自维护：

| 位置 | 形式 | 项数 | 覆盖情况 |
|---|---|---|---|
| `internal/adapter/factory.go` `Factory.Create` | switch | 13 | nexusphp/tnode/yemapt/mteam/cola/piggo/hdarea/hxpt/unit3d/gazelle/rousi/luminance + default 兜 generic |
| `internal/adapter/factory.go` `FrameworkDefaults` | map | 10 | 上述 8 项 + cola/yemapt/rousi；hdarea/hxpt/piggo 未注册（见下，属有意设计） |
| `internal/model/config_types.go:277` `FrameworkLabels` + 8 个类型常量 | map + 常量 | 8 | nexusphp/unit3d/gazelle/mteam/tnode/luminance/rousi/generic |
| `internal/model/model_test.go:335` `frameworks` | 测试内手抄切片 | 8 | 与上表完全相同 |
| `internal/adapter/factory_test.go:25` `expected` | 测试内手抄切片 | 6 | nexusphp/unit3d/gazelle/mteam/luminance/generic |
| `internal/adapter/factory_test.go:58` `cases` | 测试内手抄表 | 6 | tnode/mteam/unit3d/gazelle/rousi/luminance |
| `web/src/views/sites/SiteDetail.vue:447` `frameworkLabels` | 前端手抄 map | 11 | 上述 8 项 + cola/hdarea/hxpt；**缺 piggo、yemapt** |

已观测到的具体漂移与边界：

- `model.FrameworkLabels` / `ValidFramework`（`:288`）不认识 `cola`、`yemapt`、`piggo`、`hdarea`、`hxpt`，但这五个在 `Factory.Create` 里都有真实分支；前端标签则缺 `piggo`、`yemapt`。
- `ValidFramework` 与 `FrameworkLabels` 在全仓**仅被 `model_test.go` 引用**，生产代码零调用；8 个类型常量在生产代码也零引用（生产一律用裸字符串）。这是一座「只跟自己的测试对话」的孤岛。
- `TestFrameworkLabels_Completeness` 用测试内手抄的 8 项清单做完整性断言，因此**检测不到与 factory 真实集合的漂移**；`TestFrameworkDefaults_ContainsAll` 只断言 6 项，同样覆盖不全。
- **反例（不是缺陷）**：查 `docs/31` §59.533 刀2 与联合回归项 C，`FrameworkDefaults` 不注册 hdarea/hxpt 是「API-only 无 RSS 站不进（HashStrategy 等字段全 RSS 消费）」的明确设计；piggo 则由 migration173 在站点行上直接写 `hash_strategy=fake_from_id`/`id_strategy=path_segment` 覆盖。这三处空白不应机械补齐，但代码里没有就地注释说明，容易被误判为遗漏。

**风险**：

- 新增一个 framework 时需要改多处、且没有强制检查，漏改不会让任何测试变红（前端标签漏 piggo/yemapt 已是现成例子）。
- 测试里的「完整性」断言基准是手抄子集，给出虚假的安全感。

**建议**：

- 建立 framework 标识规约（附录G）：明确权威来源与各消费点、新增框架时的更新清单，并**写明 `FrameworkDefaults` 的有意不注册规则**。
- 补全 `FrameworkLabels`/常量至 factory 全集，并把完整性测试的基准改为单一来源（而非测试内手抄）——生产零调用，不改变运行时行为。
- 前端标签缺项属展示层文案，改动需走前端构建流程，单独评估。

### 2.2 同一概念两套词汇域：`nexusphp` 与 `np`（P2）

**证据**：

- `sites.framework`（adapter 路由域）使用 `"nexusphp"`，生产代码 92 处；`Factory.Create` 只认 `"nexusphp"`，没有 `"np"` 分支。
- `PublishFormConfig.Framework`（发布表单生成域）中，`"np"` 出现 74 次（主要在 migration 的表单配置 JSON、`publish/form_config_diff.go:119` 的草稿默认值），同时也有 4 处写成 `"nexusphp"`。
- `internal/publish/executor_stages.go` 同时读两个域：`site.Framework == "tnode"` 与 `cfg.Framework == "piggo"`，但没有 `np`↔`nexusphp` 的归一化函数（全仓搜索无 `case "np"` 或别名映射）。
- 两者在各自域内目前能跑通，但「同一个站、同一个框架概念、两种写法」没有成文边界。

**风险**：跨边界传递 framework 值时，若把表单域的 `"np"` 直接送进 `Factory.Create`，会落入 default 分支得到 `GenericAdapter("np")`，而不是 `NexusPHPAdapter`——表现是站点能力静默降级。当前调用链未发现这样的直传，属于潜在风险而非已发生缺陷。

**建议**：在附录G 中明确两个词汇域的边界与取值表；如未来需要跨边界转换，收敛到一个显式归一化函数，而不是在各处散写字符串比较。

### 2.3 URL 基址三套 helper，其中两套完全同义（P3）

**证据**：

| helper | 位置 | 语义 | 消费面 |
|---|---|---|---|
| `siteBaseURL` | `errors.go:142` | `BaseURL` 优先（去尾斜杠）→ `Domain` 含协议直用 → 裸域补 `https://` | hdarea/hdcity/hxpt/nexusphp_edit/piggo 五处；`docs/31` §59.533 附定义为公共单点（收编 hdcity 既有防御）；§59.575 又将 `HxptAdapter.base()` 的手搓拼接收编至此 |
| `resolveBaseURL` | `adapter_mteam_upload.go:276` | `BaseURL` 非空取之，否则裸取 `Domain`（无补协议/去斜杠） | 12 个文件：gazelle/cola/mteam 族/rousi/tnode/yemapt/mtorrent_core/search 等；§59.460 为可乐三面分离站引入 |
| `baseURLOf` | `adapter_generic.go:676` | 与 `resolveBaseURL` **完全相同** | 仅 generic/nexusphp_upload 两处（喂给自带补协议的 `BuildNexusDownloadURL`） |

- `baseURLOf` 与 `resolveBaseURL` 是同一逻辑两个名字，零行为差异。
- `siteBaseURL` 语义更强（补协议/去尾斜杠），历史上未覆盖到 `resolveBaseURL`/`baseURLOf` 的调用点；§59.575 表明公共单点正在逐步收编，`baseURLOf`/`resolveBaseURL` 是剩余的两个旧形态。

**风险**：`baseURLOf`/`resolveBaseURL` 重复实现，后续任一处修正容易漏改另一处；三套并存也增加「该用哪个」的认知成本。

**建议**：

- 零行为变更刀次内：让 `baseURLOf` 委托 `resolveBaseURL`，保留可乐说明注释。
- **不把 `resolveBaseURL`/`baseURLOf` 改成 `siteBaseURL`**——后者会为裸 `Domain` 补 `https://`、并去尾斜杠，属行为变更，需单独评估（且 `BuildNexusDownloadURL` 已有自己的补协议逻辑）。

### 2.4 API 请求骨架三到四处重复，可下沉到既有机制层（P3）

**证据**：

- `detailViaAPI`：`adapter_gazelle.go:164`、`adapter_mteam_detail.go:14`、`adapter_unit3d.go:212`。
- `slViaAPI`：`adapter_gazelle.go:552`、`adapter_mteam_slhr.go:499`、`adapter_unit3d.go:524`。
- `fetchUserStatsAPI`：`adapter_gazelle.go`、`adapter_mteam_upload.go`、`adapter_nexusphp_userstats.go`、`adapter_unit3d.go` 共 4 处。
- 这些方法的 HTTP 骨架一致：`http.NewRequestWithContext` → 设头 → `a.doer.Client.Do` → `defer drainBody(resp)` → `readBody(resp)` → JSON 解析；差异全在方法/URL/请求头/响应结构（方言）。
- 机制层已有 `errors.go` 的 `drainBody`/`readBody`/`networkError`/`parseError`（引用 129/102/159/58 次）与 `setCommonHeaders`（104 次），骨架部分下沉有现成落点。

**风险**：重复的骨架本身不致错，但错误包装口径已有细微差异（有的用 `networkError`/`parseError`，有的直接返回原始 err），后续统一错误处理时容易漏改。

**建议**：**不强行合并整个方法**，只考虑把 `Do → drainBody → readBody → Unmarshal → parseError` 这段纯机制抽成一个 helper，请求构造与响应结构保留在方言层——完全符合 `apihelper.go` 的既有铁律。落地前需逐点核对错误包装等价性；若核对成本高于收益，则只在附录G 里记为规约，不动代码。

### 2.5 跨包同语义小 helper（P3，渐进）

**证据**：

- `adapter_yemapt.go:564` `extractDoubanID` 与 `publish/executor_helpers.go:107` `extractDoubanID` 同名，实现不同（前者委托 `extractNumericID`，后者正则 + 纯数字兜底），语义相近但不确定等价。
- `publish/gpw_inject.go:251` 的 `gpwFirst` 注释明确写着「adapter 层 `firstNonEmpty` 同语义」，属于已知但未提取的重复。
- adapter 包内有 153 个包内私有小函数，分布在 29 个文件——数量本身不是问题，但说明「小工具散落」是常态。

**风险**：低。当前未发现因这些 helper 产生的不一致。

**建议**：遵守既有「三次法则」——出现包外消费者或第三站证明流程稳定时再升公共 util；现阶段仅在附录G 记录现状，不机械搬迁。

### 2.6 正面结论：不应被误判为问题的部分

- **接口实现同名不算重复**：12 个 adapter 的 `SearchTorrents`/`GetTorrentDetail`/`Framework` 等方法同名，是 `model.SiteAdapter` 接口的实现，属于必要结构。
- **机制层已成型**：`setCommonHeaders` 104 处、`drainBody` 129 处、`readBody` 102 处引用，说明公共 HTTP 机制早有收敛，不必重建。
- **嵌入复用已在用**：`ColaAdapter`/`Unit3DAdapter` 等嵌入 `*GenericAdapter`，是合理的复用形态。
- **`adapter/apihelper.go` 已有成文边界**：「共享机制·不共享方言」「包内私有·三次法则后再升 util」。本次治理沿用该约定，不另立标准。

### 刀1 · 纯文档 · 附录G

- **目标文件**：`docs/代码质量审计/附录G-站点适配器复用边界与框架标识规约.md`（新建），并同步 `00-总索引.md`。
- **内容**：固化 §2.1 的七处清单事实表、§2.2 的 `nexusphp`/`np` 词汇域边界、§2.3 的三套 URL 基址 helper 表、`FrameworkDefaults` 有意不注册规则（引用 `docs/31` §59.533）、新增 framework 的更新清单与三次法则。
- **验收**：事实表与本文逐项一致；不写推测；行号标注为基线快照。
- 附录E §3 计数修正已由 `5248c035` 落地，不重复做。

### 刀2 · 零行为变更代码 · `baseURLOf` 委托 `resolveBaseURL`

- **目标文件**：`internal/adapter/adapter_generic.go`（`baseURLOf` 定义位于 `:676`）；必要时在 `adapter_mteam_upload.go:276` 的 `resolveBaseURL` 注释补一句「`baseURLOf` 同义委托此函数」。
- **改动形态**：把 `baseURLOf` 的函数体替换为 `return resolveBaseURL(config)`；**不**改为 `siteBaseURL`（后者补协议/去尾斜杠，属行为变更）。
- **等价前提**：两函数当前均为「`BaseURL` 非空取之，否则取 `Domain`」，无其它分支；实施前再读一次两处实现确认。
- **验收**：`go test -count=1 ./internal/adapter/...` 全绿；`git diff` 只有上述两处。

### 刀3 · `FrameworkLabels` 补全与测试单一来源

- **目标文件**：`internal/model/config_types.go`（补 `FrameworkCola`/`FrameworkYemapt`/`FrameworkPiggo`/`FrameworkHDArea`/`FrameworkHXPT` 常量及 `FrameworkLabels` 条目）、`internal/model/model_test.go`（把 `frameworks` 手抄切片改为从权威来源派生）、`internal/adapter/factory_test.go`（`expected`/`cases` 同理）。
- **边界**：生产代码零调用 `ValidFramework`/`FrameworkLabels`/8 个类型常量，改动不影响运行时行为，但会改变测试可见 API 的返回值集合——故单列一刀。
- **不做**：前端 `frameworkLabels` 补 piggo/yemapt（需走前端三步构建，另行评估）。

### 明确不做（需专项授权）

- 三套 URL 基址统一到 `siteBaseURL`、API 骨架下沉若涉及错误包装差异修正（均为行为变更）。
- `FrameworkDefaults` 的 hdarea/hxpt/piggo 空白是设计决策，**不补**。
- 任何站点正则、方言字段映射、站方特化改动。

## 5. 本次未覆盖

## 6. 后续方向
