# 11 外部结构化输入数值边界治理

- **状态**：已完成（三刀 v0.0.1652 落地）
- **日期**：2026-11-26
- **基线**：`c31b3840`（10 全案三刀落地后，`origin/main` 最新）
- **审计范围**：`internal/` 生产代码中「外部结构化数据 → 整数长度/偏移 → 加法/截取」的数值边界纪律。核心实锤为 bencode 长度解析的整数溢出：`strconv.Atoi`/`fmt.Sscanf` 解析出 `MaxInt` 后与偏移相加回绕为负，绕过 `> len` 上界检查，导致 slice 负索引 panic。重点 `internal/client/qbittorrent/client.go:304-359`（生产活跃、HTTP 用户可控）与同型潜伏 `internal/fingerprint/bencode.go:118-136`；次要章节为解析 err 忽略导致的静默语义偏差。
- **审计方法**：全库扫描 8 类数值/解析维度（用户可控正则、整数解析、除零、slice 越界、时间解析、资源关闭、goroutine、JSON 契约），对可疑点逐行精读；对两处溢出用离线驱动构造 30 字节 bencode 复现 panic；核对上游调用链确认可达性；对照 01-10 划清正交边界。盘点确认动态正则/除零/goroutine/资源关闭/JSON 标签等维度健康，不作主导。
- **证据文件**：`evidence/tool-versions.txt`（工具版本+基线）、`evidence/bencode-overflow-repro.txt`（两处 panic 栈顶原文）。

> 本文为代码质量定点精读结论，不是安全评估结论。行号/统计为基线快照，实施前请重新定位。所有证据均来自本地离线驱动构造字节，未接触靶机或真实用户数据。

## 1. 结论摘要

- 本篇是全库盘点后新立的独立方向，治理对象是**解析算法里的数值边界**——外部数据里的长度/偏移字段如何转成整数、如何参与加法、截取前如何校验。与前序篇正交：04 管 HTTP 入参怎么解码（JSON 契约/分页/错误码），本篇管"解析算法内部的整数边界"；09 管响应体读上限与连接治理，本篇管结构化二进制数据的越界防护；01/02/03/05/06/07/08/10 分别管 Context/停机/错误/DB/测试/配置/适配器/并发，均不重叠。
- **一处高危真 bug（A-1，生产活跃）**：`internal/client/qbittorrent/client.go` 的 `findBencodeEnd` 在 `:355` 把种子字节里的长度串解析为 `int` 后直接与偏移相加得 `strEnd`，只判 `strEnd > len(data)`（上界），未判下界。当长度串为 `9223372036854775807`（MaxInt64，`Atoi` 成功）时加法回绕为负，上界检查失效，`computeInfoHash` 在 `:314` 用负值做 `torrentData[infoStart:end]` 直接 panic。离线驱动实测 `panic: slice bounds out of range [:-9223372036854775782]`。该路径经 `download_handler.go:397`（HTTP 上传/URL 下载）可达，且 reseed/pusher/seeding/watcher/orphan 多个后台 worker 同样调用——后台路径无 recovery 时可击穿进程。
- **一处同型潜伏（A-2）**：`internal/fingerprint/bencode.go:131` `decodeString` 用 `fmt.Sscanf("%d")` 解析长度后 `end := start + length`、同样只判上界。离线驱动实测 `panic: slice bounds out of range [:-9223372036854775789]`。当前 `DecodeBencode` 仅基准测试消费（同文件注释），暂非生产触发点，但属同型漏网，应与 A-1 一并补齐。
- **次要问题（B）**：`publish_torrents_handler_seed_detail.go:65-75` 两处 `time.Parse` 忽略 err，非预期布局的 `lastSeen` 退化为零值时间，导致 `cleanup_in_days` 恒为 0——静默数据错误，非崩溃。
- **正面结论**：盘点核验了动态正则（`QuoteMeta`/err 检查/RE2 线性时间，无 ReDoS）、整数除零（均有守卫）、goroutine 生命周期（带 `ctx.Done()`/`wg.Wait()`）、资源关闭（`defer Close`）、JSON 标签（敏感字段有意 `json:"-"`）等维度，均健康，不构成独立方向。
- **明确不做**：改 HTTP 输入解码契约（04 范畴）、改站点业务解析语义、加模糊测试洪泛（I0/I1 上限）、碰靶机验证。

## 2. 重点发现

### V-01 · bencode 长度整数溢出 → slice 越界 panic（高危 · CVSS 7.5 · A-1）

- **级别**：高危（技术档 CVSS v3.1 `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H` = 7.5；阅读档「高危」）——网络可达、无需认证、进程级 DoS。
- **证据**（基线 `client.go:347-359` + `:304-315`）：

```go
// findBencodeEnd
length, err := strconv.Atoi(string(data[pos : pos+colon]))   // :351 长度来自种子字节
if err != nil { return 0, err }
strEnd := pos + colon + 1 + length                            // :355 有符号加法
if strEnd > len(data) {                                       // :356 只判上界
    return 0, qbError(ErrQBParse, "string exceeds data", nil)
}
return strEnd, nil                                            // :359 返回负值

// computeInfoHash
end, err := findBencodeEnd(torrentData, infoStart)
h := sha1.Sum(torrentData[infoStart:end])                     // :314 end<0 → panic
```

  离线驱动构造 `[]byte("d4:info9223372036854775807:AAAA")` 调用 `computeInfoHash`，实测：

```
panic: runtime error: slice bounds out of range [:-9223372036854775782] [recovered, repanicked]
github.com/ranfish/pt-forward/internal/client/qbittorrent.computeInfoHash(...)
	.../internal/client/qbittorrent/client.go:314 +0x258
```

  原始输出见 `evidence/bencode-overflow-repro.txt`。

- **影响**：`computeInfoHash` panic 无就地 recover。HTTP 入口 `download_handler.go:397` 经 `AddFromFile`（`torrent.go:233`）调用，可退化成 500；reseed/pusher/seeding/watcher/orphan 后台 worker 路径（分别 `:198/:264/:683/:306/:1131`）无 HTTP recovery 兜底时 panic 击穿 goroutine、导致进程退出。Go 的整数回绕使 `> len` 上界检查对负值完全失效。
- **复现**：同包临时测试驱动调用 `computeInfoHash([]byte("d4:info9223372036854775807:AAAA"))` 即稳定 panic（探针跑完即删）。现有 `client_test.go` 覆盖 `10:short`、空串、`i42` 等常规畸形，未覆盖整数回绕分支。
- **整改**：把"先加法后判上界"改为"先判长度再加法"——`if length < 0 || length > len(data)-pos-colon-1 { return err }` 后再 `strEnd := pos + colon + 1 + length`。减法形式 `len(data)-pos-colon-1` 无溢出风险（各量非负且 `pos+colon < len(data)` 已由 `bytes.IndexByte` 保证）。同时在 `computeInfoHash` 加 `end >= infoStart` 断言作纵深防御。

### V-02 · 同型潜伏：fingerprint.decodeString 整数溢出（中危 · A-2）

- **级别**：中危（同技术特征，但当前仅基准测试消费，非生产触发点）。
- **证据**（基线 `bencode.go:118-136`）：`fmt.Sscanf("%d", &length)` 对 `MaxInt64` 解析成功（Go `fmt` 走 `ParseInt(64)`，符号扩展比对成立，不报 overflow），`end := start + length` 回绕为负，`end > len(data)` 失效。离线驱动构造 `[]byte("9223372036854775807:AAAA")` 调用 `decodeString(data, 0)`，实测：

```
panic: runtime error: slice bounds out of range [:-9223372036854775789] [recovered, repanicked]
github.com/ranfish/pt-forward/internal/fingerprint.decodeString(...)
	.../internal/fingerprint/bencode.go:136 +0x3ad
```

- **影响**：当前 `DecodeBencode` 注释标明"仅基准测试消费·未来 bencode 复用点"，暂不影响生产；但作为同型漏网，若未来接入生产路径即成为第二个 V-01。
- **复现/整改**：同 V-01，改先判 `length > len(data)-start` 再加法；纳入同批防回归锚。

### F-01 · 时间解析 err 忽略 → cleanup_in_days 静默归零（低危 · B）

- **级别**：低危（数据准确性，非崩溃）。
- **证据**（`publish_torrents_handler_seed_detail.go:65-75`）：`lastSeen, _ := time.Parse(layout, row.LastSeen)` 两次均忽略 err；非两种布局（如 SQLite 常见 `2026-11-26 10:00:00` 无时区）时退化为零值时间，`remainingDays` 钳到 0。
- **影响**：前端观察期剩余天数恒显示 0，属静默语义偏差。
- **整改**：检查 err，补 `time.ParseInLocation("2006-01-02 15:04:05", ..., time.Local)` 兜底；解析全失败时显式标注未知而非归零。

### 正面结论：经核验健康的维度（不构成方向）

逐项核验并排除：动态正则无漏网（`QuoteMeta`/`Compile`+err/embedded 冒烟校验/RE2 无 ReDoS）；整数除零均有 `if total>0` 等守卫；goroutine 均带退出路径；文件句柄均 `defer Close`；slice 索引 `FindStringSubmatchIndex` 捕获组数匹配；JSON `json:"-"` 为敏感字段有意排除。详见盘点记录，不展开。

## 3. 整改建议

- **刀1（V-01，高危）**：`findBencodeEnd` 改为先判长度上界再加法（减法形式避免回绕），`computeInfoHash` 补 `end >= infoStart` 纵深断言。
- **刀2（V-02，中危）**：`decodeString` 同批修法（先判 `length > len(data)-start`），与 V-01 共用范式。
- **刀3（防回归锚 + F-01）**：新增数值边界锚——同包临时驱动对两处各构造 MaxInt 长度字节，断言返回 error 而非 panic；纳入 06 篇 race CI 覆盖（只加测试不改基建）。锚须做阴性对照（把守卫改回裸加法→锚必须 panic，确认可触发）。F-01 时间解析兜底作为附带小修。
