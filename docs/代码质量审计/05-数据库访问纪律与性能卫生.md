## 1. 结论摘要

- 数据库访问整体已较多使用 `WithContext`（非测试代码约 689 处），但 **API 层仍有明显缺口**：`internal/api` 中约 54 处 `db.First/Find/Create/Save/Delete/Updates` 直接调用未带 `WithContext`，请求取消/超时无法传播到 DB。
- 存在少量**无界查询**风险：部分 `Find(&all)`/全表加载用于小配置表可接受，但在记录类/增长型表上需要上限、分页或流式处理。
- 已有事务先例（7 处：`client_handler` 3 处、`fingerprint/repository`、`setting/repository`、`db/migration` 2 处）；多数写入为单语句，但仍需盘点其余多步写入是否应对齐事务边界。
- 索引通过 GORM tag 和迁移逐步演进，整体有基础；热点查询是否完全覆盖仍需结合真实表规模和慢查询确认。

## 2. 重点发现

### 2.1 API 层缺少 WithContext 传播（P1）

**证据**：

- `internal/api` 非测试代码中，`h.db.First/Find/Create/Save/Delete/Updates` 无 `WithContext` 约 54 处（粗略扫描）。
- **补刀补充（v0.0.1597·用户复审发现）**：刀1 首轮词表只含终态操作（First/Find/…），漏了 builder 链起点形态（`h.db.Order/Select/Offset/Limit/Table/Raw`×22 处）——已按同款分类器补插（`h.db.DB()` 取 *sql.DB 句柄豁免·非查询）。
- 代表样例：
  - `internal/api/publish_torrents_handler_torrents.go:47,365,473`：`h.db.First(&cfg, clientUID)` 无 `WithContext`。
  - `internal/api/client_handler.go:216,358,515,581,693`：多处 `First` 无 `WithContext`。
  - `internal/api/delete_rule_handler.go:104,190,267,273,283,415`：读写/删除均无 `WithContext`。
  - `internal/api/orphan_handler.go:355`：`h.db.Find(&configs)` 无 `WithContext`、无分页/上限。
  - `internal/api/publish_torrents_handler_torrents.go:1060`：`h.db.Find(&exclusions)` 无 `WithContext`。

**风险**：

- HTTP 请求已取消或超时后，DB 查询仍可能继续执行，占用连接和资源。
- 与项目已有 Context 规范（方向 01/02）不一致，造成“上层可取消、DB 层不可取消”的断链。

**建议**：

- 以 `r.Context()` 为默认：handler 内所有 DB 调用统一 `h.db.WithContext(r.Context())...`。
- 后台任务使用 service/task ctx，不使用裸 `h.db`。
- 可先从 API 层高频 handler 开始收敛，添加简单 lint/审查规则（禁止 handler 内直接 `h.db.<op>`，除非显式说明）。

### 2.2 无界查询与全表加载（P2）

**证据**：

- `internal/site/site_data.go:237`：`db.Find(&all)` 加载所有站点后做对账；站点表规模通常可控，但调用无 `WithContext`。
- `internal/api/form_config_handler.go:166`、`internal/api/iyuu_handler.go:138,190`、`internal/api/seeding_handler_records.go:316`、`internal/api/orphan_handler.go:355`：`Find(&...)` 全量加载配置/映射类数据。
- `internal/stats/traffic_aggregator.go:29-33`：按时间窗口 `Find(&snapshots)`；有时间条件，风险取决于窗口大小与快照量。
- `internal/reseed/engine_match_prepare.go:33`：`Select("info_hash, torrent_id").Find(&seedRecords)` 全量加载做种记录索引；有 `WithContext` 和字段裁剪，但数据量增长后可能成为内存/查询压力。
- `internal/fingerprint/repository.go:162-168`：按 `pieces_hash` 查询 `Find(&fps)`，有 Where 条件，通常有界，风险较低。

**风险**：

- 增长型表全量加载会造成内存峰值、慢查询和锁竞争。
- 在请求路径上全量加载配置表通常可接受，但应明确“表规模小且有上界”的假设。

**建议**：

- 区分“小配置表”和“增长型记录表”：小表可全量但应带 `WithContext`；增长型表必须有时间窗、分页、Limit 或分批处理。
- 对 `seedRecords`/快照/记录类全表扫描评估是否可改为按需查询、分批、或专用索引+窗口。
- 为潜在大表查询补充上限保护（即使业务上“理论上不大”，也应有防御性限制）。

### 2.3 N+1 与循环查询（P2）

**证据**：

- `internal/reseed/engine_preload.go` 存在多处循环；部分为 API 调用循环（非 DB N+1），部分有分批查询（如 `chunkStrings` + 批量查询）——属于较好的模式。
- 粗略扫描未发现大量“每条记录一条 DB 查询”的典型 N+1 热点；但本次未对所有模块做完整调用图审计。

**风险**：

- 列表接口或后台批处理若引入“逐行补详情”查询，会随数据量线性放大 DB 压力。

**建议**：

- 审查列表接口：禁止在 `for range items` 内做 `First/Find`；改为 `WHERE id IN (...)` 批量查询后组装 map。
- 对确实需要逐条外部 API 调用的场景，保持 DB 批量预取 + 外部调用限速/并发控制。

### 2.4 事务边界覆盖不均（P2）

**证据**：

- 非测试代码存在 7 处显式事务，说明项目已有事务先例，并非“零起点”：
  - `internal/api/client_handler.go:299,440,524`：下载器创建/更新/删除的多步写入使用 `WithContext(r.Context()).Transaction(...)`，包含清理软删除冲突、写主记录、写路径映射、级联删除关联数据等。
  - `internal/fingerprint/repository.go:233`：`BatchSave` 使用事务批量创建指纹；事务后再同步覆盖表（事务外副作用需关注失败语义）。
  - `internal/setting/repository.go:62`：`RestoreAll` 使用事务做“清空 + 重写”。
  - `internal/db/migration.go:116`、`internal/db/migration99_tangping_name_fix.go:33`：迁移使用事务。
- 同时，仓库中仍有大量单条写入和部分多步写入未显式包事务；本次未逐条盘点所有多步写入原子性需求。

**风险**：

- 多步业务写入若中途失败，可能留下中间态；已有 `client_handler` 先例表明这类场景应优先考虑事务。
- 事务外副作用（如 `fingerprint BatchSave` 事务提交后再 `syncFetchCoverage`）若失败，会出现“主数据已提交、副作用未完成”的最终一致窗口，需要明确语义。

**建议**：

- 以 `client_handler`/`setting.RestoreAll` 为先例，盘点其余多步写入路径（发布记录、任务状态推进、导入/批量变更、清理级联等）；不能接受中间态的用 `Transaction`。
- 事务只包 DB 原子性必要段；外部调用、耗时操作放事务外，并为事务外副作用定义补偿/重试/告警语义。
- 对“事务内+事务外”混合路径补充注释，说明一致性级别。

### 2.5 索引与迁移卫生（P3）

**证据**：

- 模型层存在较多 `gorm:"index"` 标签（`internal/model/seeding.go`、`publish.go`、`reseed.go` 等）。
- 迁移代码集中在 `internal/db/migration*.go`、`internal/model/migrate_uid.go`，存在大量 `Raw/Exec`，属于迁移场景可接受。
- `AutoMigrate` 由启动/迁移流程调用（`internal/db/migration.go`、`internal/setting/migrate.go` 等）。

**风险**：

- 热路径查询条件若缺少复合索引，会随表增长退化。
- 迁移中 Raw SQL 较多，升级/回滚和跨 SQLite 版本行为需要谨慎验证。

**建议**：

- 对高频查询（按 `status + updated_at`、`info_hash + site`、`client_uid + recorded_at` 等）做索引覆盖审查。
- 迁移 SQL 保持幂等、可观测；避免在业务路径使用与迁移同风格的动态 SQL。
- 新增查询先看 explain/慢查询日志思路（即使当前 SQLite，也应关注扫描范围）。

## 4. 验证建议

- **查询抽样**：对种子记录、快照、匹配记录等增长型表执行典型查询，观察扫描行数/耗时。
- **回归测试**：为补 `WithContext` 的 handler 路径跑现有 API 测试；对事务改造补失败回滚测试。
- **观测**：必要时增加慢查询/长事务日志（按现有日志体系，不引入重架构）。
