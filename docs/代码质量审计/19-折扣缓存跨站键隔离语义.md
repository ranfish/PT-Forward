# 19 折扣缓存跨站键隔离语义

- **状态**：已精读（三刀待实施）
- **日期**：2026-11-28
- **基线**：`5eb45207`（v0.0.1673 含两笔附修·审计系列 01-18 全毕）
- **审计范围**：刷流免费状态重检缓存（`discountCache`）的键命名空间与站点隔离语义——缓存键是否覆盖被缓存事实的完整维度。确凿点：`internal/seeding/flush.go` 的 `getDiscountFromCache`/`setDiscountCache` 用裸 `torrentID` 作键，而 `torrentID` 是站点内编号（`Engine` 单例、全站共享一个 map），跨站同号种子在 TTL 窗口内互相命中对方的免费检测结果。

## 1. 结论摘要

- 本篇是 18 篇登记候选的据实复核与定题落地。三路盘点确认：最新四笔提交（v0.0.1672 截图选轨 sid 根修、v0.0.1673 八级选轨优先级及两笔附修）未产生更强的正交候选；`discountCache` 是唯一同时满足「设计权威明确 + 可纯本地离线复现 + 确凿业务决策缺陷」的方向。
- **V-01（低—中危）**：docs/31:10067 明确规定免费重检缓存键为 `(siteName, torrentID)`，实现却只用裸 `torrentID`。`Engine` 是应用单例，`discountCache` 是全站共享的单一 map；真查 `DetectDiscount` 带 `siteCfg(rec.SiteName)`，缓存读写却把站点维度丢掉。跨站同号种子在 TTL（默认 600 秒）内互相命中，两个方向都错：站 A 的 `FREE` 被站 B 命中→绕过本站重检、把实际非免费种子当免费放行下载；站 A 的 `NONE` 被站 B 命中→本该推的免费种子被漏掉。离线复现两方向均实锤。
- **正面结论**：TTL 单位/方向/边界与命中刷新健康（18 篇已核）；`discountCacheMu` 并发锁正确；同仓 `rss/engine.go:1190` 的 `siteName + ":" + event.TorrentID` 与 `engine.go:38` 的 `maindataCache map[uint]`（键=client UID）证明作者已认知维度化缓存键，本篇是 seeding 侧漏接。
- **诚实边界**：跨站实际同号 `torrentID` 的真实实例未取证（PT 站种子 ID 普遍站内自增，重号概率高，但无生产数据佐证）；未宣称发生过生产误判事故。`ClientUID` 维度缺失不构成独立缺陷——`DiscountResult` 是「站点+种子」属性，与下载器无关。
- **明确不做**：请求真实站点、碰靶机、改业务语义；本篇只做精读与整改建议，修复另案。

## 2. 重点发现

### V-01 · `discountCache` 裸 `torrentID` 键跨站串数据（低—中危 · 缓存键命名空间）

- **级别**：技术档 CVSS v3.1 `AV:N/AC:H/PR:L/UI:N/S:U/C:N/I:L/A:N` ≈ 3.1（低，按业务链可达性估）；阅读档「低—中危」——若业主把「误下载非免费种子、浪费流量/可能违反站点规则」计为实质业务损害，可按中危下限读取。**不是安全边界漏洞**：无越权、无数据泄露、无 DoS，触发需跨站同号 + TTL 窗口 + 记录处于 `IsFree && FreeEndAt==nil && Discount!=ASSUME_FREE`（`flush.go:648`）；HR 种子另有独立拦截（`flush.go:641-646`）作为部分缓解。18 篇登记的「中危」据此下调并写明理由。
- **证据**（`internal/seeding/engine.go:59-66,97`、`internal/seeding/flush.go:187-208,648-678`，基线 `5eb45207`）：

  `model.SeedingTorrentRecord`（`internal/model/seeding.go:11-14`）的 `ClientUID`/`SiteName`/`TorrentID` 是并列独立字段；`DetectDiscount(ctx, siteCfg, torrentID)` 把 `torrentID` 拼进该站详情页/API——`torrentID` 的命名空间是「每站独立」，跨站无全局唯一性。
- **设计与正例冲突**：
  - docs/31-模块设计决策记录.md:10067（Sprint 101 决策 #401(4)）：「明确免费检测 LRU 缓存键为 `(siteName, torrentID)`，最大容量 10000 条。重检时必须先清除该种子的免费检测 LRU 缓存，再调 API 获取最新结果。」实现直接违反。
  - `internal/rss/engine.go:1190`：`cacheKey := siteName + ":" + event.TorrentID`——RSS 侧同类 HR/折扣检测缓存正确带站点维度。
  - `internal/seeding/engine.go:38`：`maindataCache map[uint]*maindataEntry // §59.251: 键=client UID`——同文件对另一缓存的维度化有明确注释。
- **影响**：同一 `Engine` 单例下，各订阅/各下载器的记录全部读写同一 map。站 A 的 `FREE` 结果在 TTL 内被站 B 同号种子命中→`cached.Level.IsFree()` 为真→绕过站 B 的 `DetectDiscount`，把实际非免费的种子当免费放行下载（浪费流量、可能违反站点规则）；反向则把站 A 的 `NONE` 命中为站 B 的结论→`return candidate, false` 漏掉本该推的免费种子。两个方向都直接改变刷流推种决策。

- **整改**：把 key 改为复合键 `siteName + ":" + torrentID`（对齐 docs/31:10067 与 rss 正例）；读写两处收编为单一 helper（如 `discountCacheKey(siteName, torrentID string) string`），禁止调用方裸拼或裸索引 `e.discountCache[...]`；补跨站同号隔离锚与静态裸 key 形态锚；三阴性对照全红后实施。

### F-01 · 可达性与归因边界（信息 · 登记不主张）

- 跨站同号 `torrentID` 的真实实例未取证：PT 站种子 ID 普遍为站内自增数字，重号概率高，但本次未查到具体重号实例；是否发生过实际误判下载无生产日志证据。结论限定为「代码路径确凿可达 + 离线复现实锤」，不宣称生产事故。
- `ClientUID` 未纳入 key 不构成独立缺陷：`DiscountResult` 是站点+种子的属性，与下载器无关；同一站同一种子在不同下载器上结论相同是正确的。
- docs/31 决策 #401(4) 另规定「最大容量 10000 条」与「重检前先清缓存」——当前实现是无上限 map + 6h/30min 过期清理，与设计有偏差，但容量面未观察到实际问题（TTL 窗口内条目量受刷流规模约束），本篇登记不主张，若后续取证再单列。

### 正面结论：经核验健康、不主张的维度

- 缓存 TTL 面：`EnhancementCacheTTL`（默认 600 秒）单位/方向/`< ttl` 边界/命中刷新/过期删除均健康；`engine_stats.go:825-837` 的 30min 清理与 `archiveLoop` 6h ticker 正常。18 篇已核，本篇不重复。
- 并发面：`discountCacheMu` 在读写两处均正确 Lock/Unlock；本篇不涉及 map 并发（10 篇已治理同类）。
- 正例：`rss/engine.go:1190` 复合键、`engine.go:38` client UID 键——证明维度化缓存键是项目既有纪律，本篇是 seeding 侧漏接，不需要重写缓存框架。

## 3. 整改建议

- **刀1（V-01 根修）**：新增单一 key helper `discountCacheKey(siteName, torrentID string) string`，`getDiscountFromCache`/`setDiscountCache` 签名补 `siteName` 参数并统一经 helper 生成键；`flush.go:653/669` 两处调用点传 `rec.SiteName`；与 docs/31:10067 和 `rss/engine.go:1190` 的键形态对齐。不扩大改动面（不动 TTL、不动并发锁、不动 `DetectDiscount`）。
- **刀2（防回归锚）**：① 单元锚——键形态断言（`siteA:12345` 与 `siteB:12345` 不同键、同站同号同键）；② 端到端锚——两站同号记录依次写入/读取，站 B 不得命中站 A 条目（直接调生产 `set/getDiscountFromCache`，不 mock）；③ 静态锚——扫描生产源码禁止裸 `e.discountCache[` 索引形态与裸参数 `getDiscountFromCache(x, ...)`（须带 site 参数），点名文件行号，沿用 16/17/18 篇静态锚白名单与注释截断惯例。
- **刀3（F-01 + 三阴性）**：F-01 仅登记不误修；三阴性对照全红——A：把 key 退回裸 `torrentID` → 端到端锚 FAIL（复现串数据）；B：只改写点不改读点（半成品修复）→ 端到端锚 FAIL（读仍命中旧裸 key）；C：注入裸 `e.discountCache[torrentID]` 形态 → 静态锚点名 FAIL。恢复后工作区须干净。
