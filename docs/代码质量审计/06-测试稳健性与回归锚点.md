## 1. 结论摘要

- 测试规模较大（`internal` 下 409 个 `*_test.go`），publish/reseed/seeding 等高风险包已有成规模回归测试；但**编排不变量的锚点覆盖没有统一清单**，回归保护依赖分散测试文件。
- **CI 未启用 `-race`**：Makefile `test` 目标为 `go test -v -race -count=1 ./...`，CI `test` job 为 `CGO_ENABLED=1 go test -short -count=1 -timeout 600s ./internal/...`。并发编排代码存在数据竞争回归风险。
- 测试中共有 41 处 `time.Sleep`，0 处 `t.Parallel()`，4 处 `require.Eventually`/轮询等待类模式。部分 sleep 位于异步测试的同步点，存在环境负载下抖动风险；项目缺少统一的 fake clock/条件等待约定。

## 2. 重点发现

### 2.1 CI 缺少 race 检测（P1）

**证据**：

- `Makefile:22`：`go test -v -race -count=1 ./...`
- `.github/workflows/ci.yml:76`：`run: CGO_ENABLED=1 go test -short -count=1 -timeout 600s ./internal/...`
- `.github/workflows/ci.yml` 全文未出现 `-race`。
- 仓库存在明显并发组件：`internal/pusher/eventbus_test.go` 验证 consumer ctx 取消链；`internal/watcher/completion_watcher_test.go` 含并发 watch 与 Start/Stop；`internal/db/write_queue_test.go`、`internal/db/memory_monitor_test.go` 含异步行为；publish/reseed/seeding 亦有后台 goroutine 与共享状态。

**风险**：

- 本地开发可能通过 `make test` 发现竞争，但 PR/主干 CI 不执行 race，数据竞争可随合并进入主干。
- SQLite + CGO 下 `-race` 有额外开销，但完全不跑会把并发回归发现推迟到运行期或偶发故障。

**建议**：

- 至少在主干/夜间增加 race job，覆盖高风险包（`internal/pusher`、`internal/watcher`、`internal/db`、`internal/seeding`、`internal/reseed`、`internal/publish`、`internal/rss`），或拆分为 `race-fast` 与 `race-full`。
- 若全量 race 成本过高，保留 CI 默认 `-short` 快速反馈，同时新增非阻塞或定时阻塞的 race 工作流，并明确 owner 与清理 SLA。
- 在文档/Makefile/CI 中统一说明“本地全量”“CI 快速”“CI race”三种口径。

### 2.2 time.Sleep 驱动的异步测试存在抖动风险（P2）

**证据**：

- `*_test.go` 中 `time.Sleep` 41 处；`require.Eventually`/`assert.Eventually`/`pollUntil`/`waitFor` 仅 4 处；`t.Parallel()` 0 处。
- 代表样例：
  - `internal/watcher/completion_watcher_test.go:239,242`：`TestWatcher_StartStop` 在 Start 后 `Sleep(150ms)`，Stop 后 `Sleep(50ms)`，无状态条件断言。
  - `internal/integration/scenario_test.go:113,229,285`：启动 watcher 后固定 `Sleep(300ms)`，部分用例后续配合 `require.Eventually`，部分直接断言副作用。
  - `internal/integration/seeding_e2e_test.go:194,214,233,272`：多阶段轮询使用固定 100ms sleep。
  - `internal/pusher/eventbus_test.go:22,68`：consumer 内 sleep 模拟慢消费/取消传播；测试通过 WaitGroup 同步，语义明确，风险较低。
  - `internal/audit/logger_test.go:100,102,123`：固定 sleep 等待异步落盘/flush。
  - `internal/db/write_queue_test.go:76`：用 `time.Sleep(2 * time.Second)` 构造阻塞写请求，作为队列填充手段；可接受但会拉长单测时间。
  - `internal/httpclient/smart_dial_test.go:17,22`：模拟快慢 dial，属于行为测试；需关注 CI 慢环境下边界。
- 无 fake clock 注入模式（未检索到 `FakeClock`/`clockwork` 等）。

**风险**：

- 固定 sleep 在慢 CI、CPU 抢占、CGO/SQLite 抖动下可能产生偶发失败；失败时往往难复现。
- 过短 sleep 造成 flake，过长 sleep 拉慢测试；缺少统一等待 helper 会让新测试继续复制模式。

**建议**：

- 区分三类 sleep：**行为必要**（模拟超时/慢对端）、**同步等待**（应替换为条件轮询）、**节拍观测**（应注入 ticker/clock）。
- 对同步等待优先使用 `require.Eventually`/`assert.Eventually` 或项目内轻量 `waitFor` helper，断言可观察状态而非时间流逝。
- 对 watcher/seeding/reseed 等周期性编排，评估注入 `clock` 或可配置 tick/interval；测试中避免依赖真实 100ms+ 节拍。
- 保留行为必要 sleep 时，写明原因并尽量缩小窗口、配合上限超时。

### 2.3 高风险编排回归锚点分散，缺少覆盖矩阵（P2）

**证据**：

- 测试规模（基线快照）：`internal/publish/*_test.go` 约 10806 行，`internal/reseed/*_test.go` 约 5283 行，`internal/seeding/*_test.go` 约 5669 行，`internal/rss/*_test.go` 约 3006 行，`internal/watcher/completion_watcher_test.go` 527 行，`internal/pusher/*_test.go` 305 行。
- 存在锚点/守卫命名测试：`internal/publish/execute_branch_anchor_test.go`、`internal/publish/execute_upload_anchor_test.go`、`internal/reseed/match_gate_anchor_test.go`、`internal/reseed/misfetch_guard_test.go` 等。
- 但未见统一的“高风险编排场景矩阵”文档或测试约定；CI 只跑 `./internal/... -short`，未单独标记必须覆盖的编排不变量。

**风险**：

- 测试数量多不等于关键编排不变量被系统覆盖；重构时容易出现“局部测试全绿、跨组件编排回归”。
- 取消、重复投递、部分失败、重试、停机 drain、幂等写入等场景若无固定锚点，后续修改容易回退。

**建议**：

- 为高风险编排维护最小锚点矩阵（可放在 `docs/代码质量审计/` 附录或测试 README）：至少覆盖 Context 取消、Stop 幂等、重复事件/重复任务、部分失败补偿/日志、关键状态机迁移。
- 优先补 publish 执行链、reseed 任务取消/匹配门、seeding evaluate/flush、watcher poll/stop、eventbus close/publish 竞态的回归锚点。
- 在 PR 模板或审计文档中要求：涉及编排路径的改动必须指明对应测试锚点或新增测试。

### 2.4 CI 与本地测试口径不一致（P2）

**证据**：

- CI `test` job：`CGO_ENABLED=1 go test -short -count=1 -timeout 600s ./internal/...`（`.github/workflows/ci.yml:76`）。
- Makefile：`go test -v -race -count=1 ./...`（`Makefile:22`）。
- `testing.Short()` 跳过 4 处：`internal/metadata/fetcher_test.go:33`（“需要 DB”）、`internal/api/handler_test.go:2833,2851`（网络测试）、`internal/adapter/adapter_nexusphp_test.go:1410`（真实 HTML fixture）。

**风险**：

- 开发者本地、Makefile、CI 三套口径不一致，容易出现“本地没跑的在 CI 挂”或“CI 没跑的在生产挂”。
- `-short` 跳过网络/fixture/DB 相关测试是合理取舍，但应明确哪些测试只在本地/夜间跑，避免长期失效。

**建议**：

- 在 `Makefile` 或 `docs/` 明确测试分层：`fast`（CI 默认）、`race`、`full`（含非 short/集成）。
- 对 `testing.Short()` 跳过项定期盘点，确保被跳过测试仍可在本地/定时任务运行。
- 若保留短测策略，考虑为被跳过的关键路径提供等价的纯单测替身。

## 4. 验证建议

- **race 基线**：先在高风险包跑 `CGO_ENABLED=1 go test -race -count=1 ./internal/pusher ./internal/watcher ./internal/db ./internal/seeding ./internal/reseed ./internal/rss ./internal/publish`，记录现状，再决定是否全量。
- **flake 观测**：对含 sleep 的异步测试做多次重复运行（如 `-count=20` 定向包），观察是否有时间敏感失败。
- **锚点盘点**：为 publish/reseed/seeding/watcher 建“场景-测试文件”映射，缺口作为后续整改输入。
- **CI 口径**：在 CI 文档或 Makefile 注释中写清 `-short`、`-race`、timeout 的意图。
